## 1. Befehlsstruktur

```
postkauz <objekt> <verb> [ziel] [optionen]        Alias: pk
```

Jedes Kommando, das eine Operation des Registers ausführt, ist in `internal/cli/bindings.go` ausdrücklich an diese Operation gebunden (Tabelle, keine Ableitung). Ohne Argumente zeigt `postkauz` die Hilfe (ein interaktiver Modus ist nicht geplant).

Der Alias `pk` ist eine Kopie oder Verknüpfung der Binärdatei (`make install` legt sie an); cobra kennt für die Wurzel keine Aliase.

## 2. Beispiele

Mit „(Entwurf)" markierte Beispiele laufen erst im genannten Schnitt.

```sh
# Heute lauffähig
postkauz version --json
postkauz doctor
postkauz accounts list --json
postkauz account add demo --imap imap.example.org:993 --user demo@example.org   # Passwort wird abgefragt, landet im Schlüsselbund
postkauz account test demo                                                      # Login, Fähigkeiten, Ordnerrollen
postkauz account remove demo --dry-run

postkauz sync -a demo --full                                                    # Erstsync in Fenstern, wiederaufnehmbar
postkauz sync --watch                                                           # Dauerläufer mit IDLE
postkauz mailbox list -a demo --json
postkauz show 18233 --headers

postkauz search "from:anna after:2026-01-01 has:attachment" --limit 50 --json   # S1.7 ✓

postkauz thread 4411 --strip-quotes                                        # S1.6/S1.8 ✓
postkauz attach list 18233                                                  # S1.6 ✓
postkauz key create --name assistant-1 --role assistant --expires 90d       # S1.8 ✓, Klartext erscheint genau einmal
postkauz search Rechnung --key assistant-1 --explain                        # S1.8 ✓, Probe: was darf der Schlüssel?
postkauz audit --since 24h --actor agent --json                             # S1.8 ✓
postkauz audit export --to D:\audit-export                                  # S1.8 ✓
postkauz audit verify                                                       # S1.8 ✓, Export-Prüfsummen gegen die Datenbank

postkauz import maildir ./Mail/Archive --account demo --mailbox Archive-2024   # S1.10 ✓
postkauz import mbox "%APPDATA%\Thunderbird\Profiles\x.default\ImapMail\imap.example.org" -a demo --dry-run   # S1.10 ✓

# S2.3 ✓, Ablage im Entwürfe-Ordner S2.5 ✓
postkauz identity add -a demo --email demo@example.org --name "Demo Büro" --signature-file signatur.txt
postkauz draft reply 18233 --all --body-file antwort.md                     # Entwurf anlegen, Status draft, remote pending
postkauz sync -a demo                                                       # legt den Entwurf zuerst im Entwürfe-Ordner ab, dann Spiegel
postkauz draft show 1                                                       # remote: pushed, copies: uid 7
postkauz draft request 1                                                    # zur Freigabe vorlegen (Prüf-Hook, approval 1)
postkauz draft list --status pending_approval
postkauz approve 1                                                          # Mensch gibt den Entwurf frei (Status ready)
```

Der Mensch sendet den Entwurf in seinem gewohnten Mailclient; PostKauz erkennt den Versand beim nächsten Sync.

## 2a. Konten (S1.1)

`account add <name> --imap host[:port] --user <login> [Optionen]`

| Option | Bedeutung |
|---|---|
| `--imap` | Server als `host:port`; ohne Port 993 |
| `--user` | Anmeldename |
| `--email` | Adresse; Standard ist der Anmeldename, wenn er ein `@` enthält |
| `--tls` | `tls`, `starttls` oder `none`. Ohne Angabe: `tls` bei Port 993 (bzw. …993), sonst `starttls`; mit `--insecure-test-server` `none` |
| `--auth` | `password` (Standard), `app_password` oder seit S3.7 `oauth2` (Microsoft, siehe unten; dann kein Passwort) |
| `--client-id` | nur `oauth2`: Anwendungs-ID (Client-ID, eine GUID) der **eigenen** App-Registrierung ([betrieb_microsoft.md](betrieb_microsoft.md)); Pflicht |
| `--tenant` | nur `oauth2`: `common` (Standard), `consumers` (private Microsoft-Konten wie outlook.com), `organizations` oder eine Mandanten-ID bzw. -Domäne |
| `--insecure-test-server` | erlaubt Klartext und selbstsignierte Zertifikate, **nur** für Hosts auf dem eigenen Rechner (`localhost`, `127.0.0.1`, `::1`) |
| `--password-stdin` | Passwort aus der Standardeingabe (eine Zeile), z. B. für Skripte |
| `--password-from-env` | kein Passwort speichern; es kommt zur Laufzeit aus `POSTKAUZ_PASSWORD_<NAME>` (Server, Docker) |

Ohne `--password-stdin`/`--password-from-env` fragt die CLI das Passwort verdeckt ab; im `--json`-Modus oder ohne Terminal ist das ein Eingabefehler (Exit 2). *Seit T1c (A03 A3, Befund D5):* Unter Windows liest die Abfrage selbst über `ReadConsoleW` (Echo aus, Zeilen-Eingabe ein, Einfügen mit Strg+V oder Rechtsklick geht, Umlaute unabhängig von der Codepage), auf anderen Systemen weiter über `golang.org/x/term`; `POSTKAUZ_PASSWORD_READER=term` schaltet unter Windows auf den alten Leser zurück (Rückweg ohne neues Programm); ein anderer Wert als `console` oder `term` ist ein Eingabefehler (Exit 2), bevor die Aufforderung erscheint. Nach 120 s ohne abgeschlossene Eingabe bricht sie ab (Exit 1, Code `prompt_timeout`, Hinweis auf `--password-stdin` und die README-Zeile unter „Troubleshooting“); der Terminal-Modus wird in jedem Fall wiederhergestellt. Dasselbe gilt für die verdeckte Abfrage von `account set --password-stdin`. Zur Fehlersuche gibt es das versteckte Kommando `postkauz internal prompt-probe` (nicht in der Hilfe, keine Operation, öffnet kein Datenverzeichnis): Es liest eine Zeile wie `account add` und zeigt nur, wie sie ankam (Art von stdin, Konsolenmodus vorher/während/nachher als Flags, Codepages, Windows Terminal ja/nein, Zahl der Lesevorgänge, Bytes, Zeichen, Nicht-ASCII-, Escape- und Steuerzeichen, Zeilenende), nie den Wert und nie seinen Hash (seit der Gegenprüfung W2: ein ungesalzener SHA-256 eines echten Passworts ließe sich per Wörterbuch zurückrechnen); `--reader auto|console|term`, `--timeout` (Standard 120 s), `--expect-sha256 <hex>` (SHA-256 eines bekannten Testwerts; die Ausgabe sagt nur `hash match: yes|no`, `--json`: `hash_match` true/false, ohne die Angabe fehlt es), `--json`. Aufforderung und Ausgabe warnen: nur Testwerte, nie ein echtes Passwort (`note`). Die Messmatrix dazu: [abnahme_A3.md](abnahme_A3.md). Das Passwort wird **nie** als Kommandozeilenargument angenommen. Kontonamen: Kleinbuchstaben, Ziffern, Bindestrich (max. 63); daraus entsteht die Variable `POSTKAUZ_PASSWORD_<NAME>` (Bindestrich wird `_`).

- `account test <name>` meldet sich an, liest Fähigkeiten und Ordner (mit Rolle) und meldet sich ab; am Server ändert sich nichts. Lokal werden Fähigkeiten und Status am Konto gespeichert (`doctor` zeigt den Status). Abgelehnte Anmeldung: Exit 1, Code `auth` (kein automatischer Wiederholungsversuch); Server nicht erreichbar oder Zeitüberschreitung: Exit 5, Code `connection`.
- `account remove <name>` löscht Konto und gespeichertes Passwort. Hat das Konto archivierte Nachrichten, verweigert es das (ADR-003; Archivlöschung kommt mit dem Löschkonzept). Seit T1a prüft und löscht es in einer Transaktion unter der Kontosperre: Läuft für das Konto ein Sync oder Import, endet es mit `sync_running`, und es kann keine Nachricht zwischen Prüfen und Löschen dazukommen.
- `account set <name> --aliases a@example.org,b@example.org` (seit S2.0) setzt die **weiteren eigenen Adressen** des Kontos (Aliasse, Weiterleitungen auf dasselbe Postfach); die Liste ersetzt die vorhandene, `--aliases ""` entfernt alle. Adressen werden geprüft (nur die Adresse, ohne Namen; sonst Exit 2 `invalid alias`), klein geschrieben, sortiert, ohne Dubletten und ohne Kontoadresse und Anmeldenamen (gleich in welcher Schreibweise); höchstens 50 nach dem Entfernen (die Eingabe darf bis zu 200 Einträge haben). Ohne `--aliases` ist das ein Eingabefehler (`nothing to change`). „Eigene Adressen" sind Kontoadresse, Anmeldename (wenn Adresse) und Aliasse (ab S2.1 dazu die Identitäten): Der Betreff-Rückfall der Threads zählt sie nicht als gemeinsame Beteiligte (gilt für neu zugeordnete Nachrichten), ab S2 lässt „Allen antworten" sie weg und die Versanderkennung nutzt sie. Das Kommando ist **nur für Menschen** (HumanOnly): mit `--key`, auch einem `admin`-Schlüssel, verweigert (Exit 3, `human_only`), und es gibt kein MCP-Tool dafür. Ausgabe: `account demo: aliases a@example.org, b@example.org` bzw. `aliases none`. `accounts list` zeigt die Aliasse in der Spalte `ALIASES` (`-` ohne), `--json` im Feld `aliases` (Liste, auch leer).
- `account set <name> --password-stdin` (seit S2.1, Entscheid 36) **ersetzt das gespeicherte Passwort** eines Kontos, etwa nach einem Passwortwechsel beim Anbieter oder wenn `doctor` `password missing` meldet. Das neue Passwort kommt nur über die Standardeingabe: am Terminal mit verdeckter Eingabe (`New password for account demo:` auf stderr), sonst die erste Zeile (`Get-Content pw.txt | postkauz account set demo --password-stdin`); **nie als Argument** (ein überzähliges Argument oder `--password` ist ein Eingabefehler, Exit 2), leer ist Exit 2. Es geht in den Schlüsselbund (bzw. den unsicheren Testspeicher) unter `account/<datadir-id>/<name>`, wird zurückgelesen und verglichen; hatte das Konto noch den alten Verweis `account/<name>` (Umzug ausstehend), zeigt es danach auf den neuen, der alte Eintrag bleibt unangetastet (`doctor` meldet ihn). Ohne erreichbaren Schlüsselbund scheitert das Kommando ohne Änderung (Exit 1, `secret_store_unavailable`), zusammen mit `--aliases` ändern sich dann auch die Aliasse nicht. Ausgabe: `account demo: password replaced in the OS keyring as account/1a2b3c4d/demo`, mit `--dry-run` `dry run: would replace the password of account demo …`; ist `POSTKAUZ_PASSWORD_DEMO` gesetzt, folgt `note: POSTKAUZ_PASSWORD_DEMO is set and takes precedence over the stored password at runtime`. `--json` liefert `password` (`replaced`\|`would_replace`), `credential_ref`, `secret_store`, ggf. `env_override`, nie das Passwort. Nur für Menschen (mit `--key` Exit 3 `human_only`, kein MCP-Tool). Im Audit steht nur der Feldname `replace_password`. Danach `account test <name>` zum Prüfen.
- **Microsoft-Konten per OAuth2 (seit S3.7, E11).** Microsoft lässt IMAP nur noch mit OAuth2 zu. PostKauz bringt keine eigene App mit („bring your own client"): Der Betreiber registriert eine App in seinem Microsoft-Konto ([betrieb_microsoft.md](betrieb_microsoft.md)) und gibt deren Client-ID an. `account add outlook --imap outlook.office365.com:993 --user ich@example.org --auth oauth2 --client-id <id> --tenant consumers` legt nur das Konto an (Client-ID und Mandant stehen in der Datenbank, kein Geheimnis); es fragt kein Passwort ab (`--password-stdin` oder `--password-from-env` dazu: Exit 2). Ausgabe: `account outlook added (…); OAuth2 client <id>, tenant consumers; no token yet, sign in with: account login outlook`. **Nur mit Schlüsselbund** (Rückfrage R2): Ist er nicht erreichbar, endet `account add --auth oauth2` mit Exit 1, `secret_store_unavailable` (das Refresh-Token ändert sich bei jeder Erneuerung und lässt sich nicht über die Umgebung setzen; `POSTKAUZ_PASSWORD_<NAME>` gilt für OAuth2-Konten nicht). Der unsichere Testspeicher (`secrets.backend = "insecure-file"`) zählt nicht als Schlüsselbund: `account add --auth oauth2`, `account login`, `account test` und `sync` lehnen ihn ebenso ab (`secret_store_unavailable`), außer für Konten mit `--insecure-test-server`, deren Anmeldeadressen ebenfalls lokal sind (nur der Fake-AS der Tests; mit den echten Microsoft-Adressen nie).
- `account login <name>` meldet ein OAuth2-Konto an: Der Browser öffnet die Anmeldeseite von Microsoft (Umleitung an `http://localhost:<freier Port>`, PKCE, Frist 5 Minuten); auf stderr steht immer auch die Adresse, falls kein Browser aufgeht (`The browser opens the Microsoft sign-in. If it does not, open this address yourself:`). Mit `--device-code` gibt es keinen Browser auf diesem Rechner: stderr nennt Adresse und Code (`To sign in, open https://microsoft.com/devicelogin in a browser and enter the code ABCD-EFGH (valid until 14:05).`), die Anmeldung geht auf einem beliebigen Gerät. Danach liegt **nur das Refresh-Token** im Schlüsselbund unter `account/<datadir-id>/<name>` (ist es länger als ein Windows-Eintrag erlaubt, verteilt auf `oauthpart1g<generation>/…`, `oauthpart2g<generation>/…`, je Speichern eine neue Generation, damit ein abgebrochenes Schreiben das alte Token nicht zerstört); das Access-Token bleibt im Speicher des Prozesses und wird vor Ablauf erneuert (2 Minuten vorher; vorher liest der Prozess das gespeicherte Refresh-Token neu, falls ein anderer Prozess wie `sync --watch` es inzwischen ersetzt hat). Ausgabe: `account outlook: signed in; refresh token stored in the OS keyring as account/1a2b3c4d/outlook; access token valid until … (kept in memory only, renewed automatically)`, dann `next: account test outlook`. `--json` liefert `method` (`loopback`\|`device_code`), `refresh_token` (`stored`\|`would_store`), `credential_ref`, `secret_store`, `token_expiry`, **nie ein Token**; die Hinweise auf stderr kommen auch mit `--json`. Nur für Menschen (mit `--key` Exit 3 `human_only`, kein MCP-Tool); auf einem Passwort-Konto Exit 2. Fehler: keine Anmeldung binnen der Frist (Browser 5 Minuten, Device-Code höchstens 15 Minuten, auch wenn Microsoft keine Frist nennt), abgebrochen oder der Token-Endpunkt antwortet nach der Anmeldung nicht binnen 60 Sekunden → Exit 1, Code `login_failed`.
- Mit einem OAuth2-Konto melden sich `account test`, `sync` und `sync --watch` per SASL an (`XOAUTH2` bei Microsoft, `OAUTHBEARER`, wenn der Server es anbietet); `account test` nennt das Verfahren (`login: ok (XOAUTH2)`, `--json` Feld `auth_mechanism`). Jeder Refresh steht als Systemereignis `oauth.refresh` im Audit (`ok` oder `error` mit dem Code des Anbieters wie `invalid_grant`, nie ein Token). Mit `--dry-run` erneuern `account test` und `sync` das Access-Token für die Anmeldung, speichern das neue Refresh-Token aber nicht (das gespeicherte bleibt gültig, Microsoft widerruft es beim Einlösen nicht); `oauth.refresh` steht dann mit `"dry_run":true` in den Parametern im Audit. Lehnt Microsoft die Erneuerung ab, endet der Aufruf mit Exit 1, Code `oauth_refresh` (Abhilfe: `account login`); `sync --watch` endet dann ebenfalls (kein Wiederholen, keine Schleife); innerhalb von 5 Minuten nach einem Fehlschlag versucht derselbe Prozess es nicht erneut. Lässt sich ein erneuertes Token nicht im Schlüsselbund speichern, endet der Aufruf laut mit Code `token_not_stored` (er läuft nicht still mit dem Token im Speicher weiter). Ohne gespeichertes Token: Code `no_token`. `account set --password-stdin` gilt für OAuth2-Konten nicht (Exit 2); `account remove` löscht das Token samt Teilen. `doctor` zeigt je OAuth2-Konto `OAuth2 token stored|missing|unreadable`, den Ablauf des zuletzt ausgegebenen Access-Tokens und die letzte Erneuerung (`--json`: `auth`, `token`, `token_expiry`, `token_updated_at`); `doctor --secrets` sucht das Refresh-Token in Log, Konfiguration und Datenbank.
- `--dry-run` wirkt bei allen Kontokommandos (prüfen, nichts ändern); `account login --dry-run` startet keine Anmeldung.

## 2b. Sync, Ordner, Anzeige (S1.4/S1.5)

`sync [-a <konto>] [--full] [--watch] [--window N] [--interval D] [--idle-restart D] [--full-check-interval D] [--jobs-interval D] [--mailbox P ...]`

| Option | Bedeutung |
|---|---|
| (ohne) | Erstsync neuer Ordner in Fenstern, sonst inkrementell: neue Nachrichten, Flag-Änderungen (CONDSTORE `CHANGEDSINCE` bzw. Abgleich aller Flags), Löschungen (UID-SEARCH-Abgleich, nur wenn die Zahlen nicht passen) |
| `--full` | zusätzlich vollständiger Lösch- und Flag-Abgleich ohne `CHANGEDSINCE`; holt Fehlendes nach; prüft Nachrichten erneut, die wegen `[imap] max_message_bytes` übersprungen wurden (ohne `--full` werden sie nicht wieder angefordert) |
| `--watch` | Dauerläufer: sofort ein Lauf, danach alle `--interval` (Standard 5 min) und bei jeder IDLE-Meldung der INBOX (IDLE-Neustart alle `--idle-restart`, 5 bis 10 min, Standard 8 min); Strg+C beendet ihn |
| `--full-check-interval` | nur mit `--watch` (seit S2.0): Abstand der vollen UID-Abgleiche aller Ordner, Standard `1h`. Der erste Lauf über alle Ordner und danach der erste Lauf, der mindestens so lange nach dem letzten erfolgreichen vollen Abgleich beginnt (erfolgreich = ohne Fehler und ohne übersprungenen Ordner; sonst gleicht der nächste Lauf erneut voll ab), holt in jedem Ordner die vollständige UID-Liste (`UID SEARCH ALL`) und erkennt so auch Löschungen, die der Zahlenvergleich übersieht (z. B. wenn lokal zugleich eine Nachricht fehlt, die beim Spiegeln scheiterte). Flags bleiben inkrementell (`CHANGEDSINCE`); IDLE-Läufe (nur INBOX) gleichen nie voll ab. Der einmalige `sync` ist davon nicht betroffen |
| `--jobs-interval` | nur mit `--watch` (seit S2.5): Abstand, in dem der Dauerläufer die Tabelle `jobs` auf wartende Entwürfe prüft (Job `draft_push`), auch zwischen zwei Läufen; Standard `10s`. Ein Entwurf, den `draft new` oder ein Agent über MCP anlegt oder ändert, liegt so spätestens nach diesem Abstand plus der Dauer des APPEND im Entwürfe-Ordner (gemessen gegen die Testserver: 10,0 bis 10,3 s im ungünstigsten Fall) |
| `--window` | Nachrichten je Fenster im Erstsync (Standard 200) |
| `--mailbox` | nur diese Ordner (mehrfach möglich). Fehlt der Entwürfe-Ordner, prüft der Lauf danach keine Entwürfe auf Versand (nur den Ablauf der Freigaben; [versanderkennung.md](versanderkennung.md), Abschnitt 1) |
| `--dry-run` | meldet Ordner und lokalen Stand, schreibt nichts |

- Ausgabe ohne `--json`: Tabelle je Ordner (neu, geändert, entfernt, Fehler, gespiegelt, laut Server), am Ende genau die Zeilen `N messages mirrored` und `N errors`. Fortschritt laufender Erstsyncs steht auf stderr. `N messages mirrored` zählt die Nachrichten des Kontos, die der Server führt, ohne Dubletten über Ordner hinweg.
- Mit `--json`: ein Objekt (`account`, `mode`, `strategy`, `mailboxes[]`, `new`, `updated`, `removed`, `errors`, `messages_mirrored`, `already_known_downloaded`, `already_known_downloaded_bytes`, `linked_despite_size_difference`, `attachments_extracted`, `messages_indexed`, `index_pending`, `duration_ms`, `dry_run`); im Dauerbetrieb zusätzlich je Lauf eine NDJSON-Zeile.
- **Schon bekannt, trotzdem geladen (seit 25.10.2026, Entscheid C2):** Der Sync verknüpft eine Servernachricht ohne Inhaltsabruf, wenn lokal eine Nachricht mit gleicher Message-ID **und** gleicher Größe liegt (z. B. aus einem Import, Abschnitt 2i), seit 0.2.0-rc4 auch, wenn die lokale Kopie bis zu 6 Bytes größer ist (nächster Punkt). Sonst lädt er den Inhalt und erkennt erst danach über `content_hash` (samt Varianten am Zeilenende), dass er die Nachricht schon hat. Solche Nachrichten zählt der Bericht: ohne `--json` steht vor den Schlusszeilen eine Zeile `already known, downloaded anyway: 12 messages (3.4 MB)` (nur wenn mehr als 0), mit `--json` die Felder `already_known_downloaded` (Anzahl) und `already_known_downloaded_bytes` (Bytes; beide fehlen bei 0, im Dauerbetrieb Summe aller Runden); dazu eine INFO-Logzeile `messages already known locally` mit `downloaded_anyway`, `downloaded_anyway_bytes` und `linked_despite_size_difference`, ohne Inhalte. Typische Ursachen: Nachricht ohne Message-ID, Bestand aus einem Import vor 0.2.0-rc3 (Leerzeilen am Ende gekürzt), Server hat die Nachricht umkodiert. Ein hoher Wert nach dem Erstabgleich heißt: Es wurde unnötig viel über die Leitung geholt (bei Gmail zählt das gegen das Tageslimit). Die so geladene Rohmail bleibt ohne Verweis im Blob-Store liegen (es gibt noch keine Bereinigung des Blob-Stores); `already_known_downloaded_bytes` entspricht ungefähr diesem zusätzlichen Plattenplatz (bei komprimierter Ablage weniger).
- **Leere oder unvollständige Serverantworten (seit T1a, 0.3.0-alpha.1):** Liefert `LIST` keine Ordner oder kein INBOX, obwohl lokal Ordner bekannt sind, bricht der Lauf ab, ohne einen Ordner zu entfernen oder eine Zuordnung zu lösen (Fehler `incomplete server answer: the mailbox list from the server is empty or has no INBOX; …`; `sync --watch` versucht es im nächsten Intervall). Liefert `UID SEARCH ALL` **weniger** UIDs als `EXISTS` aus demselben `SELECT`, überspringt der Lauf diesen Ordner (zählt als Fehler des Ordners, Problemtext `incomplete server answer: UID SEARCH ALL returned N UIDs, EXISTS is M`) und löst nichts. Liefert es **mehr** (seit 0.3.0-alpha.1b, K2: zwischen `SELECT` und `SEARCH` kam Mail an), holt der Lauf die neuen Nachrichten trotzdem und lässt nur den Löschabgleich dieses Ordners aus (kein Fehler; der volle Abgleich von `sync --watch` gilt dann als nicht erledigt und läuft in der nächsten Runde erneut). Alle Fälle zählt der Bericht: ohne `--json` die Zeile `incomplete server answers: N (nothing removed; the next sync retries)`, mit `--json` das Feld `incomplete_answers` (fehlt bei 0; im Dauerbetrieb Summe der Runden), dazu je Fall eine WARN-Logzeile. Seit 0.3.0-alpha.1b hält die Datenbank die Zahl je Konto fest (Tabelle `meta`, ohne Migration), und `doctor` zeigt sie (Zeile `incomplete server answers: <gesamt> (last: <n> on <Zeitpunkt>)` unter dem Konto, JSON `incomplete_answers`, `incomplete_answers_last`, `incomplete_answers_at`) und warnt, wenn der letzte Lauf damit höchstens sieben Tage zurückliegt.
- **Verknüpft trotz kleinem Größenunterschied (seit 0.2.0-rc4, 25.10.2026, Restfall von C2):** Thunderbird ergänzt beim Speichern ein fehlendes Zeilenende am Schluss (die Kopie ist 2 Bytes größer, z. B. wenn die Servernachricht mit der abschließenden MIME-Grenze `--grenze--` ohne Zeilenende endet) bzw. eine abgeschnittene abschließende Grenze, wenn der Server sie ohne `--` und ohne Zeilenende führt (4 Bytes größer; gemessen auch 5). Der Sync verknüpft deshalb per Message-ID ohne Inhaltsabruf auch dann, wenn die lokale Kopie **0 bis 6 Bytes größer** ist als die des Servers **und** Betreff und `Date`-Kopfzeile gleich sind (Thunderbird ändert nur das Ende; eine wiederverwendete Message-ID mit anderem Inhalt wird so nicht verknüpft; fehlt `Date` auf beiden Seiten, prüft die Toleranz nur den Betreff); eine exakt gleich große Kopie hat Vorrang, sonst die mit der kleinsten Differenz. **Nie** bei Entwürfen: nicht im Entwürfe-Ordner (Rolle `drafts` oder `[draft] mailbox`), nicht für Servernachrichten mit `\Draft`, und nie an eine lokale Kopie mit `\Draft` (auch an einer Ordnerkopie), in einem Ordner mit Rolle `drafts` oder einem, in den PostKauz Entwürfe abgelegt hat, oder mit der Message-ID eines Entwurfs von PostKauz (Versand- und Übernahme-Erkennung brauchen die genaue Kopie). Entwürfe bleiben also exakt: Die Thunderbird-Fassung eines Entwurfs mit ergänztem Ende kann deshalb nach dem Sync als zweite Nachricht mit derselben Message-ID erscheinen. Ist der Server größer, gibt es keine Toleranz. Der Spiegel behält die Fassung aus Thunderbird. Ohne `--json` steht vor den Schlusszeilen `linked despite size difference: N messages` (nur wenn mehr als 0; gezählt werden verschiedene Nachrichten, nicht Ordnerkopien: eine Gmail-Mail in INBOX und „Alle Nachrichten“ zählt einmal), mit `--json` das Feld `linked_despite_size_difference` (fehlt bei 0). Gezählt wird erst, wenn die Verknüpfung gespeichert ist. **Im Dauerbetrieb** (`sync --watch`) summieren beide Zähler (`already_known_downloaded…` und `linked_despite_size_difference`) im Schlussbericht alle Runden; innerhalb einer Runde zählt jede Nachricht einmal.
- **Nach dem Abgleich** arbeitet `sync` die Warteschlange des Kontos ab (seit S1.7, Tabelle `jobs`): Text aus Anhängen extrahieren (höchstens 60 s je Lauf, der Rest im nächsten) und neue oder geänderte Nachrichten in den Suchindex aufnehmen (bis alles drin ist; Fortschritt `search index: N/M` auf stderr). Ohne `--json` steht davor die Zeile `search index: N messages indexed` (mit `, M still pending …`, wenn ein Abbruch etwas übrig ließ). Ein Abbruch verliert nichts: Der nächste `sync` macht dort weiter.
- **Abbruch** (Strg+C, `kill`, Absturz): Gespeichert ist alles bis zum letzten fertigen Fenster; derselbe Befehl setzt dort fort, ohne Doppelte. Strg+C endet mit Exit 1, Code `interrupted`. Je Konto läuft höchstens **ein** schreibender Sync: Ein zweiter (z. B. ein manueller `sync` neben `sync --watch`) bricht sofort mit Exit 1, Code `sync_running` (`another sync is running: account …`) ab, ohne sich am Server anzumelden; `--dry-run` ist davon ausgenommen. Die Sperre ist eine Dateisperre des Betriebssystems (`sync-<konto-id>.lock` neben der Datenbank) und fällt mit dem Prozess, auch nach `kill -9`.
- Am Server ändert `sync` nichts (EXAMINE, `BODY.PEEK`) — mit einer Ausnahme seit S2.5: **Entwürfe ablegen**. Zu Beginn jedes Laufs (vor dem Spiegeln, damit der Spiegel die neue Kopie im selben Lauf sieht) und im Dauerbetrieb zusätzlich alle `--jobs-interval` legt `sync` jeden Entwurf, dessen Kopie aussteht (`remote: pending`), per IMAP APPEND im Entwürfe-Ordner ab: Ordner mit Rolle `drafts` (SPECIAL-USE, sonst Name wie `Drafts`/`Entwürfe`), `[draft] mailbox` der Konfiguration überschreibt; Flags `\Draft \Seen`, die beim Anlegen vergebene Message-ID, `Date` = Zeitpunkt der Ablage. `sync` sendet nie, löscht nie, verschiebt nie. In der Textausgabe (ohne `--json`) steht vor den Schlusszeilen eine Zeile `drafts: 1 put into Drafts (flags \Draft \Seen; nothing is sent)`, ggf. mit `N taken over in the mail client (not pushed)`, `N with their copy gone`, `N ready but no longer the approved message: back to draft, not pushed (see draft show)`, `N could not be built`, `N refused by the server (see draft show)` (seit der Gegenprüfung von S2.4/S2.5: nur dieser Entwurf, die übrigen werden abgelegt; der nächste `sync` versucht ihn erneut, `sync --watch` beim stündlichen vollen Abgleich), `N found in the Drafts folder from an interrupted push (recorded, not put twice)` oder `error: no_drafts_mailbox` (kein Entwürfe-Ordner; der Lauf spiegelt trotzdem, Exit 0, der Entwurf bleibt `pending`, `draft show` nennt den Grund). Mit `--json` das Feld `drafts` (`pushed`, `taken_over`, `missing`, `approval_stale`, `failed`, `rejected`, `adopted`, `draft_ids`, `mailbox`, `error`). Im Dauerbetrieb meldet jede Ablage eine Zeile `<Zeit>  N drafts put into Drafts` auf stdout.
- **Versand erkannt, Freigabe abgelaufen, Kopie verschwunden (seit S2.6):** Nach jedem Lauf (im Dauerbetrieb nach jeder Runde) prüft `sync` die offenen Entwürfe gegen den Spiegel: Liegt die Nachricht in Gesendet bzw. „Alle Nachrichten" (gleiche Message-ID, sonst der Rückfall über Empfänger, Betreff, Zeitfenster und Text), wird der Entwurf `sent_by_human`; eine abgelaufene Freigabe setzt ihn auf `draft` zurück; ist seine Kopie aus dem Entwürfe-Ordner verschwunden, zeigt `draft list` danach `missing`. Ohne `--json` steht dann vor den Schlusszeilen eine Zeile wie `drafts: 1 sent in the mail client, now sent_by_human (1 by Message-ID; draft 3); 1 approval(s) ran out, back to status draft; 1 copy/copies gone from the Drafts folder without a matching sent message (close with draft mark-sent or draft abandon)`, mit `--json` das Feld `draft_check` (`sent_by_message_id`, `sent_by_fallback`, `approval_expired`, `missing`, `taken_over`, `sent_draft_ids`). Regeln und Grenzen: [versanderkennung.md](versanderkennung.md).
- **Ohne Verbindung** endet `sync` mit Exit 5 (`connection`); die Entwürfe bleiben `pending`, der Job ist sofort wieder fällig, und der nächste `sync` legt sie ab. Läuft für das Konto schon `sync --watch`, endet ein zweiter `sync` mit `sync_running` und überlässt dem Dauerläufer die Ablage (er hält die Kontosperre).
- **Erneute Ablage nach einer Änderung:** `draft edit` (oder `mail_update_draft`) setzt `remote` wieder auf `pending`; der nächste Push legt eine **neue** Kopie ab, seit S2.6 (Entscheid 43) aber erst, wenn der Entwurf **30 Sekunden unverändert** ist: `sync --watch` legt ihn 30 bis 40 s nach der letzten Änderung ab; ein `sync` davor legt nichts ab und meldet `drafts: 1 changed less than 30 s ago, not put yet (a running sync --watch puts it once it has been unchanged for 30 s; otherwise the next sync)` (mit `--json` `drafts.waiting`). Die erste Ablage eines neuen Entwurfs wartet nicht. Die alte bleibt im Entwürfe-Ordner (PostKauz löscht nie, kein Expunge im MVP); `draft show` nennt beide UIDs (`copies: uid 8, earlier uid 7`). Mailprogramme zeigen dann zwei Entwürfe mit derselben Message-ID; den alten löscht der Mensch im Mailprogramm.
- **Übernahme im Mailprogramm (E6):** Vor jeder Änderung und vor jeder erneuten Ablage prüft PostKauz anhand des Spiegels des Entwürfe-Ordners (vor einer erneuten Ablage frisch gespiegelt), ob die zuletzt abgelegte Kopie unverändert da ist (gleiche UID, Message-ID und Inhalts-Hash). Hat ein Mailprogramm eine bearbeitete Fassung gespeichert (neue UID, gleiche Message-ID) oder die Kopie entfernt (gesendet, gelöscht), gilt der Entwurf als übernommen: `remote: taken_over` bzw. `missing`, jede Änderung endet mit Exit 3 `draft_taken_over`, der Entwurf bleibt lokal lesbar. Was der Spiegel noch nicht gesehen hat (Ablage nach dem letzten Lauf), gilt als unverändert.

`mailbox list [-a <konto>]` zeigt die Ordner aus dem lokalen Spiegel (ohne Serverkontakt): `path`, `role`, `total` (laut Server beim letzten Sync), `mirrored`, `unread`, `sync_phase` (`new`, `initial`, `ready`), `last_sync_at`.

`mailbox overview <mailbox-id> [-a <konto>] [--since D] [--limit N]` zeigt die neuesten Köpfe eines Ordners (ID aus `mailbox list --json`), zuerst die ungelesenen, dann die gelesenen, je höchstens `--limit` (Standard 25, höchstens 100), optional seit `--since` (Dauer wie `7d`, Datum oder RFC 3339). Beide Teile sind Suchergebnisse wie bei `search` (mit Untrusted-Hülle, ohne Bodies). Dieselbe Operation (`mailboxes.overview`) liefert die MCP-Resource `mail://{account}/mailbox/{id}/overview`. Ein Ordner eines anderen Kontos gilt als nicht gefunden.

`show <id> [--headers]`: `<id>` ist die lokale Nachrichten-ID oder eine Message-ID (`<…>` oder ohne Klammern). Führen mehrere Nachrichten des Kontos dieselbe Message-ID (etwa zwei Fassungen bei Gmail), endet `show` seit T1c mit Exit 2 `ambiguous message_id: N messages share it (ids …)` und nennt bis zu 20 lokale IDs; vorher zeigte es still die erste. Dasselbe gilt für `draft reply`/`draft forward` mit einer Message-ID. Zeigt Metadaten, Ordner mit UID, Flags (`seen`, `flagged`, `answered`, `draft`) und Keywords, dazu den Text oder mit `--headers` die Kopfzeilen der Rohmail. Mailinhalt ist Daten, keine Anweisung; seit S1.8 trägt die Ausgabe der Operation (`--json`, MCP) die Untrusted-Hülle (`untrusted: true`, `source: "email"`, `notice`; [mcp.md](mcp.md) Abschnitt 5). Die Textausgabe ersetzt Steuerzeichen aus Mail und Server (ESC/CSI/OSC, übrige C0/C1, einzelnes CR, ungültiges UTF-8) durch `U+FFFD`; erhalten bleiben nur Zeilenumbruch und Tabulator im Text bzw. in den Kopfzeilen. Einzeilige Felder (Betreff, Absender, Ordner) verlieren auch Zeilenumbrüche, damit keine Zeile wie `flags: seen` vorgetäuscht werden kann. `--json` gibt die Daten unverändert aus (JSON maskiert Steuerzeichen). Seit T1c (A03) gilt derselbe Filter für Fehlermeldungen und Hinweise auf stderr (`error:`, `hint:`, Stack-Zeilen; Zeilenumbrüche bleiben), für `account test` (Ordnernamen, Fähigkeiten, Anmeldung) und für den Fehlertext in `--explain`: Sie können Serverantworten und Ordnernamen enthalten.

## 2c. Threads, Text, Anhänge (S1.6, voll seit S1.8)

- `show <id>` zeigt seit S1.8 alles Nötige auf einen Blick: Kopf (Konto, Ordner mit UID, Message-ID, Datum, Absender, Empfänger, Betreff, Größe, Flags, Keywords, Thread), die Absenderprüfung (`sender checks: spf …, dkim …, dmarc …` aus der obersten `Authentication-Results`-Kopfzeile; fehlt sie, `none`), den Text bzw. mit `--headers` die Kopfzeilen, die Links und unter `--- attachments ---` die Anhangsliste wie bei `attach list`. `--max-chars N` kürzt den Text nach N Zeichen (`[cut after --max-chars]`, `--json`: `truncated: true`).
- `show <id>` zeigt den bereinigten Text: den Klartextteil, sonst den Text aus dem HTML-Teil (`--- text (from HTML) ---`; HTML wird nie angezeigt, Links stehen als „Text <URL>"), darunter die Links mit Host und Warnungen (`punycode`, `mixed_scripts`, `ip_address`, `userinfo`, `text_domain_mismatch`). Enthielt das HTML versteckten Text, steht eine Zeile `warning: hidden text removed …` im Kopf (`--json`: `hidden_text_removed: true`). Weichen bei multipart/alternative Klartext und HTML wesentlich voneinander ab (der Klartext, den `show` und Agenten lesen, ist nicht das, was der Mailclient zeigt), steht `warning: plain text differs from the HTML part …` (`--json`: `alternative_mismatch: true`; `thread --strip-quotes`: `(plain text differs from the HTML part)`). `--strip-quotes` zeigt nur den neuen Text einer Antwort (`text_source` `plain_unquoted`/`html_unquoted`). Die Zeile `thread:` nennt den Thread.
- `thread <thread-id>` zeigt einen Thread: Betreff der ersten Nachricht, Zahl, Zeitspanne, Teilnehmer und je Nachricht ID, Datum, Absender, Betreff, Flags. `--message` nimmt stattdessen eine Nachrichten-ID; `--strip-quotes` hängt den neuen Text jeder Nachricht an. Mit `-a <konto>` gilt ein Thread eines anderen Kontos als nicht gefunden. `--max-messages N` zeigt nur die neuesten N Nachrichten (`(K older messages not shown)`, `--json`: `messages_omitted`), `--max-chars N` kürzt jeden Text.
- `attach list <message-id>` listet die Anhänge: ID, MIME-Teil, Dateiname, **erkannter** Typ (Magic Bytes), Größe, Stand der Textextraktion (`pending`, `ok`, `failed`, `skipped`) und Hinweise (`TYPE MISMATCH: declared … content is …`, `EXECUTABLE`, `inline`, `truncated`, `hidden text removed`, Grund einer übersprungenen Extraktion).
- `attach text <attachment-id> [--max-chars N] [--message ID] [-a KONTO]` zeigt den extrahierten Text. `--message` und `-a` prüfen die Zugehörigkeit: Gehört der Anhang nicht zu dieser Nachricht bzw. diesem Konto, gilt er als nicht gefunden (so prüft auch die MCP-Resource). Steht die Extraktion noch aus, extrahiert der Befehl jetzt (Subprozess mit Grenzen, siehe [sicherheit.md](sicherheit.md) Abschnitt 7) und speichert nichts (`note: extracted now; the next sync stores it`); übersprungene oder gescheiterte Anhänge nennen den Grund. Den Text speichert der Sync am Ende jedes Laufs (Zeitbudget 60 s; Ausgabe `attachments_extracted` mit `--json`).
- Fehler: unbekannter Thread oder Anhang → Exit 1, Code `not_found`; keine Zahl als ID → Exit 2.

## 2d. Suche (S1.7, Ergänzungen S1.8)

`search "<abfrage>" [-a <konto>] [--mailbox <ordner>] [--limit N] [--cursor C] [--explain] [--json [--fields a,b]]`

Durchsucht den lokalen Spiegel (ohne Serverkontakt). Ohne `-a` alle Konten. Mehrere Argumente ergeben zusammen die Anfrage (`search from:anna Rechnung`); Phrasen brauchen Anführungszeichen, in der Shell also `search '"Erdgeschoss links"'`.

| Teil | Bedeutung | Beispiel |
|---|---|---|
| Wort | findet Wortformen (Wortstamm: „Rechnungen" ↔ „Rechnung") und, ab 3 Zeichen, Teilwörter in Komposita („Vollstreck" ↔ „Zwangsvollstreckung", „steuer" ↔ „Grundsteuer"); Umlaute und ß in jeder Schreibweise („prüfen" = „pruefen", „Erdgeschoß" = „Erdgeschoss"); kürzere Wörter als Wortanfang („ab" ↔ „Abrechnung") | `Rechnung` |
| `"…"` | Phrase: Wörter direkt hintereinander (Wortformen erlaubt) | `"Erdgeschoss links"` |
| `-…` | schließt aus (Wort, Phrase oder Operator) | `steuer -grundsteuer`, `-has:attachment` |
| `from:` | Absender (Name oder Adresse, auch Teilwort) | `from:anna`, `from:"Anna Beispiel"`, `from:example.org` |
| `to:` | Empfänger (An und Cc) | `to:hausverwaltung` |
| `subject:` | nur im Betreff | `subject:Mahnung` |
| `has:attachment` | mit Anhang (`has:attachments` ebenso) | |
| `is:` | `unread`, `read`, `flagged` (auch `starred`), `answered`, `draft` | `is:unread` |
| `in:`, `mailbox:` | Ordner: Pfad (ohne Groß-/Kleinschreibung) samt Unterordnern, oder Rolle (`inbox`, `sent`, `drafts`, `trash`, `junk`, `archive`, `all`) | `in:inbox`, `mailbox:Archiv` |
| `thread:` | Nachrichten eines Threads (ID aus `show`/`thread`) | `thread:4411` |
| `tag:` | lokales Etikett (Tags ab S3) | `tag:wichtig` |
| `after:`, `before:` | Datum (`YYYY-MM-DD`, auch `YYYY/MM/DD` oder `TT.MM.JJJJ`), Mitternacht in der Zeitzone des Rechners; `after:` einschließlich, `before:` ausschließlich | `after:2026-01-01 before:2026-02-01` |

- Alle Teile sind mit **UND** verknüpft; `OR` ist ein gewöhnliches Wort (kein Operator in S1.7). Unbekannte `name:`-Präfixe bleiben Text (`Re:`, `15:00`). Fehler in Operatoren (`has:pdf`, `after:gestern`) sind Eingabefehler (Exit 2, `invalid_input`; die Meldung nennt seit S2.7 den Operator, nie den eingegebenen Wert, z. B. `after: give a date as YYYY-MM-DD`); ebenso eine leere Anfrage, mehr als 16 Suchbegriffe oder mehr als 1.024 Bytes.
- **Sortierung:** mit Suchbegriffen nach Relevanz (BM25: Betreff vor Absender vor Text vor Anhängen, Wortstamm-Treffer vor reinen Teilwort-Treffern) mal Datumsanteil (neuere Nachrichten höher); nur mit Operatoren neueste zuerst. Einzelheiten: [datenmodell.md](datenmodell.md), „Volltextsuche".
- Durchsucht werden Betreff, Absender, Empfänger, der bereinigte Text (versteckter Text ist nie im Index) und die Anhänge (Dateinamen und extrahierter Text). Auf dem Server gelöschte Nachrichten bleiben im Archiv und damit auffindbar (`deleted_remote: true`).
- **Ausgabe ohne `--json`:** Tabelle `ID`, `DATE` (Ortszeit), `FROM`, `SUBJECT` (`[attachment]` bei Anhang), darunter `N of M results (by relevance|newest first)`, bei voller Seite `more: --cursor …`, und ein Hinweis, falls Nachrichten noch nicht im Index sind (`note: N messages are not in the search index yet; run sync to finish it`). Keine Treffer: `No messages found.`
- **Mit `--json`: NDJSON, eine Zeile je Treffer** (`id`, `account`, `thread_id`, `date`, `from`, `subject`, `snippet`, `flags`, `has_attachments`, `deleted_remote`, `score`, `cursor`; seit S1.11 am Ende jeder Zeile die Kennzeichnung der Untrusted-Hülle `untrusted: true`, `source: "email"`, weil Betreff, Absender und Snippet aus Mails stammen; der Hinweis `notice` steht nur in der Textausgabe bzw. über MCP). Jeder Treffer trägt seinen Cursor: Mit `--cursor <cursor eines Treffers>` setzt dieselbe Anfrage genau dahinter fort. Mit `--explain` steht davor eine Zeile `{"explain":…,"total":…,"order":…,"index_pending":…,"next_cursor":…}`. Die Operation selbst (MCP, später REST) liefert ein Objekt mit `hits[]`, `total`, `next_cursor`, `order`, `index_pending` und optional `explain`.
- `--mailbox <ordner>` (seit S1.8) wirkt wie `in:<ordner>` in der Anfrage (Pfad samt Unterordnern oder Rolle); MCP nutzt dafür das Feld `mailbox`.
- `--fields id,subject,date` (seit S1.8, nur mit `--json`): je NDJSON-Zeile nur diese Felder und immer `untrusted`/`source` (erlaubt sind die Felder eines Treffers); unbekannte Felder sind ein Eingabefehler (Exit 2).
- `--limit` 1 bis 500 (Standard 20). Ein Cursor gilt nur für dieselbe Anfrage und dasselbe Konto (sonst Exit 2); er ist undurchsichtig.
- **Cursor sind kein Schnappschuss.** Ein Cursor merkt sich Bewertung und ID des letzten Treffers sowie die Uhrzeit der ersten Seite (für die Aktualitätsgewichtung), nicht den Index. Ändert sich der Index zwischen zwei Seiten (ein Sync spiegelt neue Mails, der Index-Job arbeitet nach, eine Nachricht wird neu aufbereitet oder nach einer neuen Index-Version neu aufgebaut), verschieben sich die BM25-Werte: Ein Treffer kann dann auf zwei Seiten stehen oder auf keiner, neue Nachrichten erscheinen erst bei einer neuen Suche, und `total` kann sich von Seite zu Seite ändern. Wer vollständige Listen braucht, sucht ohne laufenden Sync (`sync --watch` anhalten) oder mit großem `--limit` in einem Zug. Stabiler ist die Sortierung nur nach Datum (Anfrage nur mit Operatoren): Neu gespiegelte Nachrichten mit aktuellem Datum stehen vor dem Cursor und erscheinen erst bei einer neuen Suche.
- `--explain` (seit S1.8 eine globale Option, Abschnitt 2g) zeigt bei `search` zusätzlich die Übersetzung: je Suchbegriff Feld, Art (`stem` Wortstamm, `prefix` Wortanfang, `phrase`, `substring` nur Teilwort) und die beiden FTS5-Ausdrücke (Wortindex und Trigram), die Filter, ignorierte Teile und die SQL-Anweisung mit Platzhaltern (`?`; der Suchtext steht nur in den Parametern).
- Ins Audit kommen nur Zahl der Suchbegriffe, Art der Operatoren, `limit` und ob Cursor/Explain/Ordner gesetzt waren; nie der Suchtext.

## 2e. API-Schlüssel und Probe der Policy (S1.8)

`key create --name <name> [--role reader|assistant|operator|admin] [--scopes s1,s2] [--expires 90d|never] [--dry-run-default=false]`

- Legt einen Schlüssel für einen Agenten an (Scope `admin`, nur der Mensch; nicht über MCP). Rollen und Scopes wie [sicherheit.md](sicherheit.md) Abschnitt 2; Standard `assistant`. `--scopes` **verengt** die Rolle (z. B. `--role reader --scopes mail:search` für einen Triage-Agenten ohne Bodies); ein Scope außerhalb der Rolle ist ein Eingabefehler. Laufzeit Standard 90 Tage (`--expires never` ohne Ablauf); `dry_run_default` ist an (schreibende Aufrufe laufen als Trockenlauf, bis der Agent `dry_run: false` setzt).
- Der Schlüssel (`pk_key_` und 43 Zeichen) erscheint **genau einmal** in der Ausgabe (`--json`: Feld `secret`). Gespeichert wird nur sein SHA-256; `key list` zeigt ihn nie, auch nicht den Hash. Verloren: `key revoke` und neu anlegen.
- `key list` zeigt Name, Rolle, Scopes, Status (`active`, `expired`, `revoked`), Trockenlauf-Standard, Anlage, Ablauf und letzte Nutzung.
- `key revoke <name>` widerruft sofort; der Name bleibt belegt (eindeutiges Audit). Ein zweiter Widerruf meldet `already revoked`.
- **`--key <name>`** (global): Der Mensch handelt mit den Rechten dieses Schlüssels, z. B. `search Rechnung --key test-agent --explain` oder `policy show --key test-agent`. So lässt sich vor dem Einsatz prüfen, was ein Agent sehen würde. Erwartet wird der **Name**; ein Schlüssel im Klartext als Argument wird abgewiesen (Exit 2; Kommandozeilen sind in der Prozessliste sichtbar). Unbekannt: Exit 1 `not_found`; widerrufen oder abgelaufen: Exit 3 `denied`. Im Audit steht `key:<name>`.
- `policy show` beschreibt die Richtlinie des (mit `--key` gewählten) Schlüssels: Rolle, Scopes, Trockenlauf-Standard, Ablauf, Zeichenbudget für Agenten (`[agent_defaults] max_chars` der Policy-Datei, Standard 20.000; seit S2.1) und die erlaubten Operationen mit Risikostufe. Ohne `--key` ist das der Mensch (`cli`, alle Rechte). Seit S2.3 (Entscheid 40) folgt für einen Schlüssel der Block `never with a key (human only):` mit je einer Zeile `  <operation>: human_only` (z. B. `drafts.approve: human_only`), `--json` im Feld `human_only` (für den Menschen leer): Diese Operationen darf kein Schlüssel, gleich welcher Rolle.

## 2f. Audit (S1.8)

- `audit [--since 24h] [--until …] [--actor human|agent|system] [--key-id key:<name>] [--operation <name>] [--result ok|denied|needs_approval|error] [--limit N] [--after-id N]` zeigt Einträge: ID, Zeit, Akteur, Schlüssel (`cli` für den Menschen, `key:<name>` für API-Schlüssel), Operation, Ergebnis (mit Grund und `dry-run`), Ziele (z. B. `message:42`) und Parameter **ohne Inhalte** (Feldnamen, Zähler; nie Suchtext oder Mailtext). Zeitangaben: Dauer rückwärts (`10m`, `24h`, `7d`), Datum (`2026-10-16`) oder RFC 3339; Standard die letzten 24 Stunden. `--json`: NDJSON, ein Eintrag je Zeile. Bei voller Seite `more: --after-id N`.
- `audit export [--to <ordner>]` schreibt das Audit tageweise (UTC) als JSONL-Dateien `postkauz-audit-JJJJ-MM-TT.jsonl` (0600) an einen **zweiten Ort** (anderer Datenträger oder Rechner, z. B. ein Google-Drive- oder Netzwerkordner) und hält je Tag Prüfsumme, erste/letzte Eintrags-ID und Ort in `audit_exports` fest. Ohne `--to` gilt `[audit] export_dir` (Abschnitt 5). Ein noch laufender Tag wird bei jedem Export neu geschrieben (`updated`). Passt eine früher exportierte Datei nicht mehr zu ihrer Prüfsumme, überschreibt der Export sie nicht (Exit 1, Code `mismatch`): Der Beleg einer Manipulation bleibt. **Seit T1a (0.3.0-alpha.1):** Ein Tag, der nach seinem Ende (Mitternacht UTC) exportiert wurde, ist abgeschlossen und wird nie wieder geschrieben. Ein verspäteter Eintrag mit dem Zeitstempel eines abgeschlossenen Tages (etwa der Abschluss eines `sync --watch`-Laufs, der vor Mitternacht begann) kommt in die Datei des nächsten offenen Tages; `audit verify` rechnet mit derselben Zuordnung. Am Ziel ersetzt der Export nur eigene Dateien: Liegt dort unter einem seiner Namen eine Datei, die weder der Nachweis in `audit_exports` noch das Manifest am Ziel als eigene ausweist, oder ein fremdes Manifest, bricht er ab, bevor er etwas schreibt (`the target directory holds a file this program did not write`). **Format 2 (seit S1.11):** jede Zeile ist `{"event":{…},"prev":"…","chain":"…"}` mit `chain = SHA-256(prev + "\n" + event)`; die Kette läuft über alle Tage (erste Zeile eines Tages hängt an der letzten des Vortags, ganz am Anfang der feste Startwert `SHA-256("audit-chain-v1")`). Daneben schreibt der Export das **Manifest** `postkauz-audit-manifest.json` (je Datei Tag, Zahl der Einträge, IDs, Prüfsumme, Kettenende; dazu der Startwert und das Ende der ganzen Kette, keine Zeitangabe). Die Ausgabe nennt das Manifest und `chain head: …` (wer sich diesen Wert notiert, kann spätere Exporte dagegen prüfen). Exporte im Format 1 (S1.8 bis S1.10, eine Zeile je Eintrag ohne Kette) prüft `verify` weiter; der nächste Export schreibt sie im Format 2 neu.
- `audit verify` prüft jede exportierte Datei gegen ihre Prüfsumme (`export file was changed`), ihr Vorhandensein (`export file is missing`), die Hash-Kette in der Datei (`hash chain is broken`), das Manifest (`manifest is missing`, `manifest does not match the recorded exports`) und die Zeilen der Datenbank (`database rows differ from the export`); wo möglich mit der ersten betroffenen Zeile, z. B. `export file was changed (line 2)`. Ergebnis `ok: N exported days checked; …` mit `chain head: …` (Exit 0) oder `mismatch: …` (Exit 1, Code `mismatch`). Eine geänderte Datenbankzeile betrifft nur ihren Tag, nicht die späteren (deren Kette wird an der unveränderten Exportdatei fortgesetzt). Tage mit neueren, noch nicht exportierten Einträgen nennt die Zeile `not exported yet (new entries): …` (kein Fehler; `verify` selbst erzeugt einen Eintrag).
- **Täglich** (seit S1.11): Windows-Aufgabe über `deploy/windows/Register-AuditExport.ps1`, unter Linux der systemd-Timer `deploy/systemd/postkauz-audit-export.timer`; beide rufen `postkauz audit export --quiet` (Ziel aus `[audit] export_dir` bzw. `--to`). Einrichtung: README, „Daily audit export". `doctor` meldet den letzten Export (Zeile `audit:`). Seit S2.0/A7 trägt das Windows-Skript `--data-dir` und `--config` mit den Pfaden ein, die `doctor` beim Einrichten zeigt, und bricht ab, wenn Windows sie in den Ordner eines App-Pakets umleitet (Abschnitt 5).

## 2g. Erklären, leise, Profile (S1.8)

- **`--explain`** (global) schreibt nach jedem Aufruf eine Zeile auf **stderr**: Operation, Scope, Risiko, Schlüssel, Entscheidung der Policy mit Grund, Trockenlauf und die **Audit-ID** des Eintrags, z. B. `explain: messages.search (scope mail:search, risk R0) as key key:leser: allow (ok), dry run no; audit event 42`. Mit `--json` als Zeile `{"explain":{"operation":…,"scope":…,"risk":…,"key":…,"actor":…,"decision":…,"reason":…,"dry_run":…,"audit_id":…}}`. Auch verweigerte Aufrufe werden erklärt. Inhalte stehen nie darin; stdout bleibt die Ausgabe der Operation.
- **`--quiet`**, `-q`: keine Fortschrittszeilen (Sync, Suchindex) auf stderr; Ergebnis und Fehler bleiben.
- **`--profile <name>`**: getrennte Instanz mit eigener Konfiguration und eigenen Daten (Abschnitt 5). Gedacht für Probe- und Abnahmedaten neben dem Alltag.
- **`--config <datei>`** und **`--data-dir <ordner>`** (seit S2.0/A7): Konfigurationsdatei bzw. Datenverzeichnis für diesen Aufruf, mit Vorrang vor `POSTKAUZ_CONFIG`/`POSTKAUZ_DATA_DIR` und `data_dir` in der Datei. Relative Pfade gelten ab dem aktuellen Ordner, ein abschließender Trenner fällt weg; leere Werte, eine nicht vorhandene `--config`-Datei und `--config` zusammen mit `--profile` sind Eingabefehler (Exit 2; `--profile` nimmt `profiles/<name>/config.toml` neben der normalen Konfigurationsdatei). Gedacht für geplante Aufgaben, die genau die Pfade brauchen, die `doctor` im Fenster zeigt (`Register-AuditExport.ps1` schreibt sie in die Aufgabe).

## 2h. MCP-Server (S1.9)

`postkauz mcp` startet den MCP-Server über stdin/stdout für einen Agenten (lesend; mit `mail:draft` seit S2.8 auch Entwürfe) (Claude Code, Claude-App, andere MCP-Clients). Tools, Resources, Prompts und Hülle: [mcp.md](mcp.md); Einrichtung: README, „Set up MCP in Claude Code".

- **Schlüssel** nur aus der Umgebung: `POSTKAUZ_KEY` (der Schlüssel aus `key create`) oder `POSTKAUZ_KEY_FILE` (Pfad zu einer Datei mit dem Schlüssel; unter Linux/macOS nur für den Nutzer lesbar, sonst Exit 1). Nie als Argument; `--key` ist bei `mcp` ein Eingabefehler (Exit 2).
- Fehlt der Schlüssel oder ist er unbekannt, widerrufen oder abgelaufen, startet kein Server: Exit 3 (`denied`), Grund auf stderr, nichts auf stdout.
- Die Tool-Liste folgt den Scopes des Schlüssels (`reader`: 9 Tools; verengt auf `mail:search`: nur Suche und Richtlinie; seit S2.8 mit `mail:draft`, also `assistant` und höher: 15 Tools, dazu die 6 Entwurfs-Tools). Es gibt kein Tool zum Senden, Löschen, Verschieben, Freigeben, Ablehnen oder Verwerfen. Entwürfe legt der Server nur lokal an; in den Entwürfe-Ordner bringt sie `sync` (ADR-009).
- Jeder Tool-Aufruf und jedes Lesen einer Resource steht im Audit mit `key:<name>` und Akteur `agent`, ohne Mailtext (`postkauz audit --key-id key:<name>`).
- `--profile` und `POSTKAUZ_DATA_DIR` wählen die Datenbank wie bei jedem Kommando. Der Server synct nicht; aktuell hält die Daten `sync` bzw. `sync --watch`.
- Log: Start, Ende und je Aufruf Tool, Schlüssel und Audit-ID in `postkauz.log` (ohne Inhalte); stdout gehört allein dem Protokoll.

## 2i. Import aus mbox und Maildir (S1.10)

```
postkauz import mbox <datei|ordner> [-a KONTO] [--mailbox ZIEL] [--labels-from ORDNER]... [--rescan] [--no-extract] [--dry-run]
postkauz import maildir <ordner>    [-a KONTO] [--mailbox ZIEL] [--labels-from ORDNER]... [--rescan] [--no-extract] [--dry-run]
```

Liest einen Bestand in ein Konto ein, ohne den Server zu berühren (Operation `import.run`, Scope `admin`, R1; nur der Mensch an der CLI, kein MCP-Tool, weil sie beliebige lokale Dateien liest).

- **Abgleich über Identität, nicht über Datum** (ADR-003): Gibt es die Nachricht im Konto schon (gleicher `content_hash`; dabei zählen auch Varianten mit einem Zeilenende mehr oder weniger am Schluss sowie mit keinem, einem und zwei), wird sie nicht doppelt gespeichert; sie bekommt nur den Ordner des Imports zugeordnet (`existing`). Ihre Flags bleiben die des Servers. Sonst wird sie neu angelegt (`new`) und läuft durch dieselbe Aufbereitung wie beim Sync (Parser, Bereinigung, Anhänge mit Typprüfung, Threads); am Ende laufen Extraktion und Suchindex (siehe „Textextraktion" unten). Eine nur importierte Nachricht zeigt `show` mit „deleted on server: not on the server (imported only)". **Gleiche Message-ID allein reicht nicht** (seit 0.2.0-rc6, 25.10.2026): Gmail führt teils zwei verschiedene Nachrichten mit derselben Message-ID in „Alle Nachrichten" (z. B. die Fassung des Absenders mit Outlook-Kopfzeilen und die empfangene mit `ARC-*`/`Delivered-To`). Ist die Message-ID schon bekannt, liest der Import die Nachricht zuerst nur zum Hashen (nichts wird geschrieben) und vergleicht den Inhalt: Passt er (oder ist sie die Thunderbird-Fassung einer schon gesyncten Nachricht: am Ende 1 bis 6 Bytes länger, gleicher Betreff und `Date`, Abschnitt 2b), ist sie `existing`; sonst liest er sie noch einmal und legt sie als eigene Nachricht an (`new`). Bis 0.2.0-rc5 wurde die zweite Fassung verworfen und vom Sync erneut geladen; ein so entstandener Bestand bekommt sie mit `import … --rescan` nachträglich (der Sync verknüpft danach beide Serverkopien ohne Inhaltsabruf, je mit der Fassung gleicher Größe). Das zweite Lesen geht über dasselbe Datei-Handle und muss denselben Inhalt ergeben; hat ein anderes Programm (Thunderbird beim Kompaktieren) die Datei inzwischen an Ort und Stelle geändert, zählt die Nachricht als `errors` mit Hinweis `message changed between two reads …` und wird nicht gespeichert; die Quelle gilt trotzdem als erledigt, erst `import … --rescan` holt die Nachricht. Unter Windows kann Thunderbird die Datei während des Imports nicht ersetzen (sie ist ohne Freigabe zum Löschen geöffnet) und kompaktiert danach; unter Linux und macOS liest der Import nach einem Ersetzen weiter die alte Datei. Eine **Teilkopie** (Thunderbird hat nur einen Teil geladen, Bit 0x0400) einer Nachricht, deren Message-ID schon da ist, wird nicht als eigene, abgeschnittene Nachricht gespeichert, sondern zugeordnet (Hinweis `only partly downloaded by Thunderbird; linked …`). Kommt die Teilkopie zuerst (früherer Ordner oder Lauf), bleibt sie eine eigene Nachricht neben der später importierten vollen Fassung.
- **Ordner:** Importierte Ordner sind eigene, lokale Ordner neben denen des Servers (der Sync löscht sie nie). `show` nennt sie mit „(imported)", die Suche findet sie mit `in:<pfad>` (auch Unterordner) und `in:import` (alles Importierte). `mailbox list` zeigt nur die Ordner des Servers.
- **Zielordner:** Bei einer einzelnen Datei bzw. der Wurzel eines Maildirs ist `--mailbox` der Ordner (ohne Angabe: Dateiname bzw. `INBOX`); bei einem Verzeichnis ist es das Präfix der Ordner darunter (ohne Angabe: Pfade relativ zum Verzeichnis).
- **Thunderbird** (Profilordner `ImapMail/<server>` oder `Mail/Local Folders`, Ablage „mbox"): Jede Datei, die mit einer Trennzeile `From ` beginnt, ist ein Ordner; Unterordner liegen in `<ordner>.sbd/` und werden zu `<ordner>/<unterordner>`; Ordnernamen in Thunderbirds IMAP-UTF-7 werden dekodiert (`Entw&APw-rfe` → `Entwürfe`); `.msf`-Index- und andere Dateien werden übersprungen (`files ignored`). Aus `X-Mozilla-Status` werden Flags (gelesen, beantwortet, markiert), aus `X-Mozilla-Keys` Schlagwörter; **gelöscht markierte Nachrichten (Bit 0x0008) werden übersprungen** (`skipped`); die `X-Mozilla-*`-Zeilen und das `>From`-Quoting werden entfernt, damit die Nachricht der Kopie des Servers gleicht. **Leerzeilen am Ende** (seit 0.2.0-rc3, Entscheid C2 vom 25.10.2026): Von den Leerzeilen vor der nächsten Trennzeile bzw. vor dem Dateiende entfernt der Import genau **eine** (sie gehört zum mbox-Rahmen); weitere bleiben Teil der Nachricht, und die letzte Zeile bekommt kein Zeilenende ergänzt. Zeilenenden (CRLF/LF) bleiben, wie sie sind. So ist die gespeicherte Nachricht Byte für Byte die des Servers, ihre Größe stimmt, und der erste Sync verknüpft sie über Message-ID und Größe, ohne sie erneut zu laden (vorher wurden alle Leerzeilen am Ende entfernt; in einer echten Thunderbird-INBOX traf das 16 % der Nachrichten, die der Sync dann ganz neu lud). Fehlt die Rahmen-Leerzeile (manche mboxrd-Quellen, letzte Nachricht einer Datei), hält der Import eine echte Leerzeile für den Rahmen; die Größe weicht dann um ein Zeilenende ab, der Sync lädt die Nachricht und findet sie über `content_hash` (Varianten ein Zeilenende mehr oder weniger), ohne Doppelte. Nachrichten aus einem älteren Import behalten ihre gekürzte Form; der Abgleich findet sie weiter über die Varianten von `content_hash`, ein erneuter Import erzeugt keine Doppelten. Ein mbox-Eintrag, der nur aus der Rahmen-Leerzeile besteht (zwei Trennzeilen mit einer Leerzeile dazwischen), zählt jetzt als `skipped` mit Hinweis `empty message`; bis 0.2.0-rc2 wurde er als Nachricht aus einem Zeilenende importiert. Nur teilweise heruntergeladene Nachrichten (Bit 0x0400) werden mit Hinweis importiert. Andere mbox-Dateien (z. B. Gmail-Export) werden als mboxrd gelesen.
- **Maildir:** Jede Datei wird Byte für Byte übernommen (seit 0.2.0-rc3: nichts am Ende gekürzt oder ergänzt; nur `X-Mozilla-*`-Kopfzeilen werden wie bei mbox entfernt). `cur/` und `new/`; Flags aus dem Dateinamen hinter `:2,` (unter Windows auch `!2,`/`;2,`): S, R, F, D; mit T markierte Dateien und Dateien in `tmp/` (laufende Zustellung) werden übersprungen. Unterordner im Maildir++-Stil (`.Archiv.2024` → `Archiv/2024`) und im Thunderbird-Stil (`<ordner>.sbd/`).
- **Labels (`--labels-from`)**: Nachrichten dieser Ordner werden **nur zugeordnet**, nie gespeichert; was dort nicht schon vorhanden ist, zählt als `skipped` (eine andere Fassung mit bekannter Message-ID mit Hinweis `same Message-ID as a stored message but different content; not stored (labels only)`). Gedacht für Gmail, wo „Alle Nachrichten" alles enthält und INBOX, Gesendet, Wichtig und jedes Label Kopien derselben Mails sind. Dateien, die schon als Inhalt gelesen werden, werden dabei übergangen. Beispiel (PowerShell, Thunderbird-Profil):

  ```powershell
  $tb = "$env:APPDATA\Thunderbird\Profiles\<profil>\ImapMail\imap.gmail.com"
  postkauz import mbox "$tb\[Gmail].sbd\Alle Nachrichten" -a gmail --mailbox "[Gmail]/Alle Nachrichten" --labels-from $tb --dry-run
  ```

- **Große Dateien, Wiederaufnahme:** Dateien werden gestreamt (im Speicher höchstens ein Kopf von 1 MiB und ein Stapel Metadaten; gemessen in [import_messung.md](import_messung.md)). Je Stapel (200 Nachrichten bzw. 32 MiB) wird die Position in der Datei mit den Nachrichten gespeichert; nach einem Abbruch (Strg+C, Absturz, `kill -9`) setzt derselbe Aufruf dort fort (`(resumed)`). Eine fertig importierte Quelle mit gleicher Größe wird beim nächsten Lauf nicht wieder gelesen (`unchanged`); eine gewachsene mbox-Datei wird ab der gespeicherten Position weitergelesen. `--rescan` liest alles neu (findet nichts doppelt, kostet nur Zeit).
- **Textextraktion der Anhänge** (seit 0.2.0-rc6): Nach dem Einlesen arbeitet `import` die Extraktion **bis zum Ende** ab (der Sync hat dafür nur 60 s je Lauf; nach einem großen Import warteten sonst Tausende Anhänge über mehrere Syncs). Fortschritt auf stderr `attachment text: N/M`, höchstens einmal je Sekunde; danach die Zeile `attachment text: N attachments extracted` (mit `, M still pending (the next sync continues)`, wenn etwas offen blieb), mit `--json` `attachments_extracted` und `extract_pending`. Die Grenzen je Anhang (Zeit und Größe im Unterprozess) bleiben. Strg+C ist sicher: Fertige Anhänge bleiben, der Rest bleibt `pending` und wird vom nächsten Sync erledigt. `--no-extract` überspringt das Abarbeiten; dann gilt wie beim Sync nur das Zeitbudget von 60 s. Bei großen Beständen kann die Extraktion **Stunden** dauern; die Suche (auch in Anhängen) ist erst nach Extraktion und Index vollständig. Vor der Extraktion läuft schon der Index der neuen Nachrichten (seit 0.2.0-rc7), sie sind also gleich suchbar. Bei Strg+C zeigt `import` trotzdem seinen Bericht bis dahin (mit `extract_pending`, `index_pending`, mit `--json` als Objekt auf stdout mit `interrupted: true`) und endet mit Exit 1, Code `interrupted`.
- **Fortschritt** je Datei auf stderr (Prozent, Größe, MB/s; bei Maildir Dateien), höchstens einmal je Sekunde; `--quiet` schaltet ihn ab.
- **`--dry-run`** liest alles und zählt, schreibt aber nichts (keine Nachricht, keine Datei im Blob-Store, kein Stand).
- **Sperre:** Ein Import sperrt das Konto wie ein Sync; läuft `sync --watch` für dasselbe Konto, endet der Import mit `sync_running` (Exit 1), und umgekehrt.
- **Ausgabe:** je Quelle eine Zeile, danach Hinweise und als letzte Zeile die Zählung, z. B.

  ```
  import maildir into account demo (2.1s, 4.9 MB, 2.3 MB/s)
  SOURCE    FOLDER           MODE     NEW  EXISTING  SKIPPED  ERRORS
  Mail      Archive          content  700  300       3        0
  1 files ignored (not mbox, e.g. Thunderbird .msf index files)
  search index: 700 messages indexed
  new: 700, existing: 300, skipped: 3, errors: 0
  ```

  Ein zweiter Lauf zeigt `new: 0`. Mit `--json` ein Objekt nach dem `OutputSchema` von `import.run` (je Quelle `new`, `existing`, `skipped`, `errors`, `linked`, `bytes`, `resumed_at`, `unchanged`, `problems`; gesamt zusätzlich `linked`, `sources_unchanged`, `files_ignored`, `attachments_extracted`, `extract_pending`, `messages_indexed`, `index_pending`). `errors` zählt Nachrichten, die nicht gelesen oder gespeichert werden konnten (z. B. über 256 MiB); der Lauf geht weiter (Exit 0).
- **Eingabefehler** (unbekanntes Format, Pfad fehlt, kein mbox/Maildir gefunden): Exit 2. Im Audit stehen Konto und Feldnamen, nie Pfade.

## 2j. Entwürfe, Freigaben, Identitäten (S2.3, vollständig seit S2.7)

Draft-only (ADR-002): **PostKauz sendet nie.** Ein Entwurf wird lokal gespeichert; seine Kopie legt der Job `draft_push` in den Entwürfe-Ordner (seit S2.5: `sync` zu Beginn jedes Laufs, `sync --watch` alle `--jobs-interval`, Abschnitt 2b). Der Mensch sendet im Mailclient. Seit S2.7 vollständig (u. a. `draft show --eml`, Warnung vor älteren Kopien); die Kommandos decken alle Felder der Operationen ab.

- **Wer darf was:** Anlegen, Ändern, Lesen und Vorlegen brauchen den Scope `mail:draft` (Rollen `assistant`, `operator`, `admin`; mit `--key` eines `reader`-Schlüssels Exit 3 `missing_scope`). `approve`, `reject`, `draft abandon`, `draft mark-sent` und `identity …` darf **nur der Mensch ohne `--key`**: mit jedem Schlüssel, auch `admin`, Exit 3 `human_only`, nichts ändert sich.
- **Freigabe:** `draft request` legt eine Freigabe an (gültig `[draft] approval_ttl`, Standard 7 Tage, danach fällt der Entwurf beim nächsten Lesen oder `sync` auf `draft` zurück). `approve` setzt `ready`, wenn sich der Entwurf seit der Vorlage nicht geändert hat; jede Änderung danach setzt ihn auf `draft`, die Freigabe auf `superseded`, und ein `approve` der alten Freigabe endet mit Exit 3 `approval_stale`. Seit der Gegenprüfung von S2.3 bindet die Freigabe auch die **fertig gebaute Nachricht** (`message_hash` in `draft request --json` und `approval show --json`): `approve` baut den Entwurf neu; hat sich seit der Vorlage etwas geändert, das erst beim Bau dazukommt (Signatur oder Reply-To der Identität, die zitierte Ausgangsnachricht, Anhänge), fällt der Entwurf auf `draft` zurück, die Freigabe wird `superseded`, Exit 3 `approval_stale`; dann `draft request` erneut. Ändert jemand den Entwurf, während `draft request` ihn prüft (Prüf-Hook), legt `draft request` nicht vor: Exit 3 `draft_changed`. Ein Entwurf ohne jeden Empfänger (To, Cc und Bcc leer) darf entstehen (der Mensch ergänzt mit `draft edit <id> --to <adresse>`; `draft new`/`reply`/`edit` zeigen dann `warning: the draft has no recipient …`, in `--json` unter `warnings`), `draft request` legt ihn aber nicht vor und startet keinen Prüf-Hook: Exit 3 `no_recipients` (seit der Gegenprüfung von S2.9). `draft edit` ändert nur die genannten Felder auf dem jeweils aktuellen Stand (ändert ein anderer Prozess gleichzeitig, wird neu gelesen und zusammengeführt; nach drei vergeblichen Versuchen Exit 3 `draft_changed`).
- **Fachliche Ablehnungen** sind Exit 3 (`denied`) mit Grund in der Meldung, z. B. `denied (approval_stale): …`, `draft_closed` (Entwurf verworfen oder gesendet), `draft_taken_over`, `draft_changed`, `no_recipients`, `attach_outside_dir`, `attach_not_found`, `hidden_text_in_draft`, `invalid_address`, `too_large`, `too_many_recipients`; dazu ein Hinweis mit dem nächsten Schritt. Unbekannte Entwürfe, Freigaben und Identitäten: Exit 1 `not_found`. Widersprüchliche Eingaben (z. B. `--body-file` und `--html-file`): Exit 2.
- **Dateinamen mit `=?`** (seit S2.7): Ein Anhangname, der wörtlich wie ein kodiertes Wort aussieht (z. B. `=?utf-8?q?=E2=80=AE?=gpj.exe`), wird beim Bau selbst kodiert, wie Betreff und Namen seit der Gegenprüfung von S2.3; der Empfänger sieht genau den Namen, den `draft show` zeigt. Umgekehrt dekodiert der Spiegel Dateinamen eingehender Mails genau einmal (wie Mailclients); vorher konnte `attach list` bei solchen Namen etwas anderes zeigen als der Mailclient, und eine Weiterleitung übernahm den falschen Namen. Schon gespiegelte Nachrichten behalten ihren gespeicherten Namen bis zu einem neuen Einlesen.
- **Prüf-Hook** (seit S2.4): `draft request` startet vor der Vorlage das Programm aus `[draft] check_hook` der Policy-Datei (Abschnitt 5). Exit 0 = `pass`; sonst bleibt der Entwurf `draft`, und `draft request` zeigt die Ausgabe des Hooks. Sie stammt vom eigenen Programm des Betreibers, steht aber nie im Audit oder Log; dort nur `hook: pass|fail|timeout|error`. `draft show` zeigt das letzte Ergebnis (`hook:`).
- **Trockenlauf** (`--dry-run`): `draft new|reply|forward` zeigt die Vorschau ohne zu speichern (`dry run: would create a draft (reply) in account demo, status draft; nothing saved`), `draft request` prüft nur (der Prüf-Hook läuft dabei mit: `dry run: hook: …`), `approve` usw. melden, was geschähe.
- **Audit:** je Aufruf ein Eintrag des Executors und je Übergang ein Eintrag mit Grund `transition` (Draft-ID, Art, Zustand vorher/nachher, Zahl der Empfänger und Anhänge, Freigabe, Hook-Ergebnis); nie Betreff, Adressen, Text oder Dateinamen. `audit --since 10m --operation drafts.request_ready` zeigt sie.
- `--json` liefert die Ausgabe der Operation (`source: "draft"`, `draft_id`, `status`, `preview`, `original`, `attachments`, `warnings`, `remote`, `remote_note`, `preview_hash`, …). Seit S2.8 enthalten `preview.text` und bei `draft show --json` `body_text` nur den eigenen Text mit Signatur; Zitat bzw. Weiterleitung stehen getrennt in `original` (Untrusted-Hülle, [mcp.md](mcp.md) Abschnitt 5). Die Textausgabe zeigt beides wie bisher hintereinander. Seit der Gegenprüfung von S2.8 (W3) nennt `derived_from_email` (`untrusted`, `source: "email"`, `notice`, `fields`) die Felder, die aus der Ausgangsnachricht übernommen wurden (`subject`, `to`, `cc`, `in_reply_to`, `references`, `attachments`; in `draft list --json` je Eintrag), und Warnungen zu Anhängen nennen die Stelle statt des Namens (`warning: attachments[0] is a program or script (…)`).
- **Ablage (S2.5):** `remote: pending` heißt: Die Kopie wartet auf den nächsten `sync` (ein laufender `sync --watch` legt sie nach höchstens `--jobs-interval` ab). Ein Entwurf in `ready` wird nur abgelegt, wenn die jetzt gebaute Nachricht (bis auf `Date`) die freigegebene ist; sonst kein Push, der Entwurf fällt auf `draft` zurück, die Freigabe wird `superseded`, und `draft show` erklärt es (`push: not pushed while ready …`); erneut vorlegen mit `draft request`. Danach wird er wie jeder Entwurf beim nächsten Push abgelegt. `draft abandon` und `draft mark-sent` lassen die Kopie im Entwürfe-Ordner (kein Löschen); abgeschlossene Entwürfe werden nie abgelegt. Seit der Gegenprüfung von S2.4/S2.5: `draft request` und `approve` prüfen, ob die Kopie im Entwürfe-Ordner noch genau die Nachricht ist, die vorgelegt bzw. freigegeben wird (z. B. nach dem Entfernen der Identität oder einer neuen `quote_line`); wenn nicht, wird eine neue Kopie eingereiht (`remote: pending`), die alte bleibt im Ordner. Lehnt der Server einen Entwurf ab, sagt `draft show` `push: not pushed: the mail server refused …` statt „within 10 s"; der nächste `sync` (bzw. `sync --watch` beim stündlichen vollen Abgleich) versucht es erneut, eine Änderung sofort. Wird ein Entwurf verworfen, während seine Kopie gerade abgelegt wird, bleibt die Kopie (`push: a copy (uid N) reached the Drafts folder just after the draft was closed …`); löschen kann sie nur der Mensch im Mailclient.
- **Ältere Kopien im Entwürfe-Ordner** (seit S2.7, Entscheid 43): Nach jeder Änderung legt der Push eine neue Kopie ab; die alte bleibt, weil PostKauz nichts löscht. Solange laut Spiegel ältere Kopien desselben Entwurfs (gleiche Message-ID, ältere UID; neueste ist die zuletzt abgelegte oder eine noch neuere, die der Mailclient gespeichert hat) im Ordner liegen, warnen `draft show` (`warning: older copies in Drafts: 2 (delete them in your mail client; postkauz never deletes)`, `--json`: `older_copies`, `older_copy_uids` und der Text in `warnings`) und `draft list` (siehe Tabelle). Die Zahl stammt aus dem Spiegel: Was der Mensch im Mailclient löscht, verschwindet nach dem nächsten `sync` aus der Warnung. Kopien in anderen Ordnern (z. B. Gmail „All Mail") zählen nicht. Ab S2.6 legt der Push einen geänderten Entwurf erst ab, wenn er 30 Sekunden unverändert ist (weniger Zwischenstände); das Löschen alter Kopien entscheidet S3.
- **`draft show <id> --eml`** (seit S2.7): schreibt statt der Übersicht die Nachricht als RFC-5322-Text auf stdout (CRLF, sonst nichts; umleitbar: `postkauz draft show 1 --eml > entwurf.eml`). Gebaut wird sie wie beim Push, mit der `Date`-Kopfzeile der abgelegten Kopie (`pushed_date`); ist der Entwurf seitdem unverändert, sind es **Byte für Byte** die Bytes der Kopie im Entwürfe-Ordner (belegt gegen den IMAP-Server im Prozess und seit der Gegenprüfung S2.6–S2.8 im Integrationstest `TestIntegrationDraftPush` gegen Dovecot, Stalwart und GreenMail, je nach erster und zweiter Ablage, Kopie per FETCH vom Server). Was die Bytes sind, steht auf stderr: `note: eml: byte for byte the copy (uid 7) that postkauz put into the Drafts folder`; nach einer Änderung (am Entwurf, an Identität, Signatur, Zitat oder Anhängen) `note: eml: the draft … changed after the copy (uid 7) was put into the Drafts folder; this is the current draft with the Date of that copy` (der nächste Push legt eine neue Kopie ab); vor dem ersten Push `note: eml: not in the Drafts folder yet; Date is the time the draft was created, the push sets its own`. Hat der Mensch die Kopie im Mailclient geändert oder entfernt, wird das angehängt. Alle Warnungen, die `draft show` sonst zeigt (Anhangtyp nach Entscheid 39, ältere Kopien im Entwürfe-Ordner nach Entscheid 43), stehen ebenfalls als `note: …` auf stderr (Gegenprüfung S2.6–S2.8, K8). Mit `--json` steht die Nachricht im Feld `eml` (7-Bit-Text: Kopfzeilen RFC-2047-kodiert, Text quoted-printable, Anhänge Base64), dazu `eml_date`, `eml_matches_copy` (`true` nur bei Gleichheit) und `eml_note`; ohne `--eml` fehlen diese Felder. Die Operation ist `drafts.get` mit `"eml": true` (Scope `mail:draft`, R0).

## 3. Maschinenlesbarkeit (`--json`)

- **Ein Ergebnis = ein JSON-Objekt** auf stdout, einzeilig. Listen, die streambar sein sollen (Suche, Audit), liefern **NDJSON** (ein Objekt je Zeile) ab S1.
- **Dieselben Felder wie MCP und REST.** Die Ausgabe ist die serialisierte Ausgabe der Operation (ihr `OutputSchema`); es gibt keine CLI-eigene Form. Die Registerversion steht in `postkauz version --json` (`schema_version`). Ausgaben mit Mailinhalt (`show`, `thread`, `search`, `attach list`, `attach text`) tragen oben die Untrusted-Hülle `untrusted`, `source`, `notice` (seit S1.8). Der Vertragstest `TestCLIContractRegistry` prüft jede Eingabe, die ein Kommando baut, gegen das `InputSchema` und jede `--json`-Ausgabe gegen das `OutputSchema` der Operation; `TestBindingsCoverCatalogAndSchemas`, dass jede Operation genau ein Kommando hat und jedes Feld des `InputSchema` über ein Argument oder eine Option erreichbar ist.
- **Fehler** als JSON auf stderr: `{"error":{"code":"…","message":"…","hint":"…"}}`. Codes: `usage`, `invalid_input`, `denied`, `needs_approval`, `unknown_operation`, `exists`, `not_found`, `auth`, `connection`, `secret_store_unavailable`, `no_secret`, `no_token`, `token_not_stored`, `oauth_refresh`, `login_failed`, `schema_too_new`, `migration_blocked`, `database_busy`, `schema_mismatch`, `policy_invalid`, `interrupted`, `sync_running`, `mismatch`, `prompt_timeout`, `internal`, `error`. `migration_blocked` und `schema_mismatch` (seit T1a): Eine Migration steht an, aber ein anderer Prozess hat die Datenbank offen (seit 0.3.0-alpha.1b jeder Prozess über die Prozesssperre `<datenbank>.lock`: `sync --watch`, MCP-Server, Audit-Export, ein anderes Kommando; Prozesse bis 0.2.0-rc8 nur als Sync oder Import über `sync-<konto-id>.lock`), bzw. die Datenbank wurde von einem anderen Programmstand migriert (gleiche Migrationsnummer, anderer Name); in beiden Fällen ändert das Programm nichts. `database_busy` (seit 0.3.0-alpha.1b): Ein anderer Prozess migriert die Datenbank gerade; das Kommando hat 5 s gewartet und nichts getan. `prompt_timeout` (seit T1c, A3): Die verdeckte Passwortabfrage bekam 120 s lang keine abgeschlossene Eingabe (Exit 1; Hinweis auf `--password-stdin`). `internal` heißt: Das Programm ist abgestürzt (Panic, ein Fehler im Programm); die Meldung nennt nur die Meldung der Go-Laufzeit oder den Typ des Panic-Werts, nie dessen Inhalt; ein bereinigter Stack (Funktionen und Datei:Zeile, ohne Argumente) steht auf stderr bzw. im Log (Exit 1). Ohne `--json` stehen Fehler als Zeilen `error: …` und `hint: …` auf stderr; Steuerzeichen werden zu U+FFFD, und seit der Gegenprüfung T1c (K5) sind Folgezeilen einer Meldung oder eines Hinweises um vier Leerzeichen eingerückt, damit ein Zeilenumbruch aus einer Serverantwort oder einem Ordnernamen keine eigene Zeile `hint: …` vortäuscht.
- **Ablehnungen** haben seit S2.7 bei jedem Kommando dieselbe Form, ob die Policy ablehnt oder der Handler: `denied (<grund>): …`, z. B. `denied (missing_scope): drafts.update needs the scope mail:draft, which the key does not have`, `denied (human_only): drafts.approve is for a human without a key`, `denied (approval_stale): …` (vorher bei der Policy `ops: drafts.update: deny (missing_scope)`). Der Grund steht in Klammern immer an derselben Stelle; mit `--json` im Feld `message` (Code `denied`, Exit 3). Eine nötige Freigabe hieße entsprechend `needs_approval (<grund>): …` (Exit 4); in S2 kommt das nicht vor (Entscheid 44, Abschnitt 4).
- **Keine interaktiven Rückfragen im `--json`-Modus.** Fehlt eine nötige Bestätigung, endet der Aufruf mit Exit-Code 2 oder 4; er blockiert nie. Das ist wichtig für Agenten, die die CLI statt MCP nutzen.
- **Keine Geheimnisse in der Ausgabe** (Test mit Kanarienwerten ab S1).
- `--cursor` gibt es seit S1.7 bei `search` (Abschnitt 2d), `--fields id,subject,date` seit S1.8 (nur `search`); `--explain` ist seit S1.8 global (Abschnitt 2g).
- **Eingaben prüft der Executor** gegen das `InputSchema` der Operation (seit S1.8, für CLI und MCP gleich): falscher Typ, Wert außerhalb der Grenzen, unbekanntes Feld → Exit 2, Code `invalid_input`; der Aufruf steht trotzdem im Audit (`error`, Grund `invalid_input`). Die Meldung nennt nur Feld und Regel (z. B. `invalid input: account: does not have the expected form`, `kind: not an allowed value (one of: …)`), **nie den eingegebenen Wert** und nie den Namen eines unbekannten Felds; Zahlen und erlaubte Werte stammen aus dem Schema (seit der Gegenprüfung von S2.3). Grenzen der Entwurfsfelder (Betreff 500, `body_markdown`/`body_html` 200.000, Anzeigename 200, Begründung von `reject` 2.000 Zeichen) prüft der Handler: Überschreitung ist `denied` mit Grund `too_large` (Exit 3), wie A02 es vorgibt. Ins Log (`postkauz.log`) schreibt ein gescheiterter Aufruf nur Operation, Code und Grund, nie die Meldung. Seit S2.7 gilt das für **alle** Eingabefehler, nicht nur die des Schemas: Suche (Operatoren, `--fields`), `account add` (Host, Port, `--tls`, `--auth`), `key create` (Name, Rolle, Scope, `--expires`), Zeitangaben von `audit`, IDs (`draft show abc`), `import` (Format) und `--config` nennen Feld und Regel, nie den Wert oder Pfad.

## 4. Exit-Codes

Festgelegt in `internal/cli/exit.go`, getestet in `internal/cli/contract_test.go`: `TestExitCodesMatchDocs` liest diese Tabelle und die Liste der Fehlercodes (Abschnitt 3) und vergleicht sie mit dem Code; `TestExitCodesEndToEnd` löst die Codes 0, 1, 2, 3 und 5 mit echten Aufrufen aus. Exit 4 kommt in S2 nicht vor (Entscheid 44): Keine Operation hat Risiko R3, und die Freigabe eines Entwurfs ist ein eigener Schritt (`draft request` endet mit Exit 0 und Status `pending_approval`, eine verweigerte Freigabe mit Exit 3).

| Code | Name | Bedeutung |
|---|---|---|
| 0 | `ExitOK` | erfolgreich |
| 1 | `ExitError` | allgemeiner Fehler; auch Abbruch per Strg+C (`interrupted`) |
| 2 | `ExitUsage` | Eingabefehler (unbekanntes Kommando oder Flag, fehlendes Argument, ungültige Eingabe der Operation) |
| 3 | `ExitDenied` | Scope oder Policy verweigert |
| 4 | `ExitNeedsApproval` | Freigabe erforderlich (für Operationen mit Risiko R3, ab S3; in S2 nicht erreichbar) |
| 5 | `ExitConnection` | Verbindung zum Server fehlgeschlagen oder Zeitüberschreitung (Watchdog) |

## 5. Konfiguration und Pfade

- **Konfigurationsdatei** (TOML, optional): `POSTKAUZ_CONFIG`, sonst `<Konfigurationsordner des Betriebssystems>/postkauz/config.toml`. Unbekannte Schlüssel sind ein Fehler. Inhalt:

  ```toml
  data_dir  = ""            # leer = Standard des Betriebssystems (siehe unten)
  log_level = "info"        # debug | info | warn | error
  [secrets]
  backend = "auto"          # auto | keyring | insecure-file (UNSICHER, nur Testserver)
  [imap]                    # Watchdog (ADR-007, Nachtrag 16.10.2026); Dauer als Text
  command_timeout = "30s"       # so lange darf der Server während eines Kommandos schweigen (ab 1s)
  command_max_duration = "10m"  # Obergrenze je Kommando (nicht kleiner als command_timeout)
  max_message_bytes = 268435456 # größte Rohmail in Bytes (Standard und Höchstwert 256 MiB, Mindestwert 1 MiB = 1048576, seit S2.0); größere (laut Server) fordert der Sync nicht an: einmal Fehler dieser Nachricht, danach gemerkt bis zum nächsten `sync --full`; der Rest läuft weiter. Seit T1a gilt dasselbe für einen **Kopf über 1 MiB** (fest, nicht einstellbar; Problemtext `header larger than the limit`); Köpfe eines Abrufs zusammen höchstens 16 MiB, der Rest kommt mit dem nächsten Abruf; seit T1c (A5.3) nennt der Bericht sie in einer eigenen Zeile `N skipped (larger than <Grenze> bytes, [imap] max_message_bytes); not fetched, counted as errors; raise the limit and run sync --full to fetch them` (mit `--json` `skipped_too_large` und `max_message_bytes`), und `account add` gibt einen Hinweis mit Beispiel (10 MiB) aus
  [audit]
  export_dir = ""           # Standardziel von `audit export`: ein zweiter Ort, nicht das Datenverzeichnis
  [paths]                   # seit S2.1
  attach_dir = ""           # Dateianhänge von Entwürfen nur von hier (A02 E10); leer = <Datenverzeichnis>/attach, relativ = zum Datenverzeichnis; Symlinks werden aufgelöst (Ziel muss in attach_dir liegen, sonst attach_outside_dir), nur reguläre Dateien (FIFO, Gerät, Ordner: attach_not_found; docs/sicherheit.md)
  [operator]                # seit S2.1
  name = ""                 # wer freigibt (approvals.decided_by); leer = Benutzername des Betriebssystems
  [draft]                   # seit S2.1 (gewirkt ab S2.2–S2.6); nicht zu verwechseln mit [draft] der Policy-Datei
  approval_ttl = "168h"     # so lange gilt eine offene oder erteilte Freigabe (1m bis 8760h)
  max_attachment_bytes = 26214400  # Summe der Anhänge eines Entwurfs (Standard 25 MiB, höchstens 256 MiB)
  mailbox = ""              # Ordner für die Entwurfskopien; leer = Ordner mit Rolle drafts
  quote_line = "On {date}, {from} wrote:"  # Einleitung des Zitats; nur {date}, {date_numeric} und {from}, eine Zeile
  ```

- **Zitatzeile auf Deutsch** (`[draft] quote_line`, Platzhalter `{date_numeric}` seit S2.4): Programmausgaben sind Englisch, deshalb beginnt ein Zitat standardmäßig mit `On Wed, 21 Oct 2026 09:15 +0200, Erika Beispiel <erika@example.org> wrote:`. Die Vorlage kennt drei Platzhalter: `{date}` (Datum der Ausgangsnachricht englisch, wie oben), `{date_numeric}` (dasselbe Datum als `21.10.2026 09:15`, in derselben Zeitzone wie `{date}`, also der der Ausgangsnachricht, siehe unten; fehlt das Datum, steht `??.??.???? ??:??`) und `{from}` (Absender als `Name <adresse>`). Für Deutsch:

  ```toml
  [draft]
  quote_line = "Am {date_numeric} schrieb {from}:"
  ```

  ergibt `Am 21.10.2026 09:15 schrieb Erika Beispiel <erika@example.org>:`. Datum und Uhrzeit stehen in der Zeitzone der Ausgangsnachricht (ihrer `Date`-Kopfzeile), nicht in der des Rechners (seit der Gegenprüfung von S2.4/S2.5: sonst bauten CLI und Sync-Dienst mit verschiedenen Zeitzonen verschiedene Nachrichten). Ein anderer Platzhalter (z. B. `{datum}`) oder ein Zeilenumbruch ist ein Fehler beim Start (Exit 1, Meldung ohne den Wert). Die Zeile wirkt, sobald PostKauz die Nachricht baut (neuer Entwurf, `draft edit`, `draft request`, `approve`); ändert man sie zwischen Vorlage und Freigabe, passt die Freigabe nicht mehr (`approval_stale`, dann `draft request` erneut).

- **Policy-Datei** (seit S2.1, A02 E8): `policy.toml` im selben Ordner wie die Konfigurationsdatei (mit `--profile` im Profilordner), `POSTKAUZ_POLICY` überschreibt den Pfad (dann muss die Datei existieren). Aufbau und Wirkung: [sicherheit.md](sicherheit.md), Abschnitt 5. Jedes Kommando, das die Datenbank öffnet (auch `mcp`), lädt und prüft sie; eine ungültige Datei (unbekannter Schlüssel, ungültiger Wert, Syntaxfehler) hält es auf: Exit 1, Code `policy_invalid`, die Meldung nennt Datei, Zeile und Schlüssel, nie Werte. Ändert sich ihr Inhalt, trägt das nächste Kommando eine neue Version in die Tabelle `policies` ein; die Version steht in jedem Audit-Eintrag (`policy_version` in `audit --json`).

- **Prüf-Hook in der Policy-Datei** (seit S2.4, A02 E4; Regeln: [sicherheit.md](sicherheit.md), Abschnitt 5): `[draft] check_hook` ist eine **Liste** aus Programm und Argumenten, kein Shell-Befehl; das Programm als absoluter Pfad oder als Name auf `PATH`. In den Argumenten stehen Platzhalter für Dateien, die PostKauz je Lauf in einem frischen Temp-Ordner anlegt und danach löscht: `{eml}` (die fertige Nachricht), `{body_html}`, `{body_text}` (Text der Nachricht, UTF-8), `{meta_json}` (Betreff, Absender, Empfänger, Message-ID, Anhangsnamen und -größen, Konto, Identität). Dieselben Pfade stehen in `POSTKAUZ_DRAFT_EML`, `POSTKAUZ_DRAFT_BODY_HTML`, `POSTKAUZ_DRAFT_BODY_TEXT`, `POSTKAUZ_DRAFT_META_JSON`. Exit 0 = bestanden. `check_hook_timeout` (Standard `"30s"`) begrenzt die Laufzeit; danach wird der Hook samt Kindprozessen beendet (`hook: timeout`). Fehlt das Programm: `hook: error` (nie `pass`). Leere Liste (Standard) = kein Hook. Beispiele im Repository unter `deploy/hooks/` und seit S2.9 in jedem Release-Paket (`check-example.ps1`, `check-example.sh` neben den Programmen, mit Prüfsumme in `SHA256SUMS`; Entscheid 42) (scheitern, wenn der Betreff `TODO` enthält oder die Anrede fehlt: Die erste nicht leere Zeile des Texts muss, Leerzeichen am Anfang nicht gezählt, mit `Hallo`, `Guten Tag`, `Sehr geehrte`, `Liebe`, `Lieber`, `Dear` oder `Hi` beginnen; einfacher Vergleich des Zeilenanfangs mit genauer Groß- und Kleinschreibung, „Sehr geehrter" zählt mit, „Hilfe" leider auch, „hallo" nicht):

  ```toml
  # Windows (Windows PowerShell 5.1); einfache Anführungszeichen lassen die Backslashes stehen
  [draft]
  check_hook = ['powershell.exe', '-NoProfile', '-NonInteractive', '-ExecutionPolicy', 'Bypass',
                '-File', 'C:\PostKauz\hooks\check-example.ps1', '{meta_json}', '{body_text}']
  check_hook_timeout = "30s"

  # Linux, macOS (anstelle des Windows-Eintrags)
  [draft]
  check_hook = ["sh", "/opt/postkauz/hooks/check-example.sh", "{meta_json}", "{body_text}"]
  ```

  Ein eigener Linter steht nur in der eigenen Policy-Datei, nie im Repository. Unter Windows startet der Hook ohne Konsolenfenster; Stapeldateien (`.bat`, `.cmd`, auch mit Punkt oder Leerzeichen am Ende wie `lint.bat.`, die Windows als `lint.bat` startet) lehnt PostKauz ab (sie liefen über `cmd.exe`), ein PowerShell-Skript läuft über `powershell.exe -File`. **Umlaute in der Begründung:** PostKauz liest die Ausgabe des Hooks als UTF-8. Windows PowerShell 5.1 schreibt umgeleitete Ausgabe aber in der OEM-Codepage (z. B. 850), aus „ä" würde dann Unsinn. Ein eigenes PowerShell-Skript setzt deshalb am Anfang `[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false` (wie `check-example.ps1`); PowerShell 7 (`pwsh.exe`) schreibt ohnehin UTF-8. Die knappe Umgebung des Hooks (nur `PATH`, `HOME`/`USERPROFILE`, `TEMP`/`TMP`, `SYSTEMROOT`, `LANG`) reicht: Windows PowerShell 5.1 startet damit, `ConvertFrom-Json` und `Get-Content` laufen (Teilabnahme S2.4 auf Windows, 22.10.2026). Bricht die CLI hart ab (Taskmanager, `kill -9`), bleibt ein Temp-Ordner `postkauz-hook-*` liegen; der nächste Hook-Lauf löscht solche Ordner, wenn sie älter als eine Stunde sind.

- **Profile** (`--profile <name>`, seit S1.8): Konfiguration und Daten liegen in einem Unterordner `profiles/<name>` des normalen Konfigurations- bzw. Datenordners (auch unter `POSTKAUZ_CONFIG` und `POSTKAUZ_DATA_DIR`), z. B. `%LOCALAPPDATA%\postkauz\profiles\test\postkauz.db`. Setzt die Profil-Konfiguration `data_dir`, gilt genau dieser Ordner. Namen wie Kontonamen. Seit S2.0 (A2) hängt der Eintrag im Schlüsselbund am Datenverzeichnis (`account/<datadir-id>/<name>`); zwei Profile mit gleichem Kontonamen haben getrennte Einträge.
- **Umgeleitete Pfade unter Windows** (seit S2.0/A7, Befund D3.3c): Läuft PostKauz in einem App-Paket (MSIX, z. B. gestartet aus der Claude-Desktop-App), legt Windows neue Ordner unter `%LOCALAPPDATA%` und `%APPDATA%` in Wahrheit unter `…\Packages\<Paket>\LocalCache\…` an; die Aufgabenplanung und jedes andere Programm sehen dort einen anderen, leeren Ordner. `doctor` erkennt das an der Datei-Identität (Windows zeigt die Umleitung sonst nirgends) und meldet den echten Pfad (Zeile `really:`, JSON `data_dir_real` bzw. `config_path_real`), den Paketnamen (`package:`, JSON `app_package`) und eine Warnung; liegt das Datenverzeichnis noch nicht vor, warnt er vorab. Umgekehrt meldet er in einem normalen Fenster eine Kopie gleichen Namens mit Datenbank im Paketordner, die er nicht sieht (JSON `data_dir_shadow`). Vorhandene Daten erst in den neuen Ordner kopieren, dann umstellen. Abhilfe: Datenverzeichnis außerhalb dieser Ordner, z. B. `--data-dir C:\PostKauz\data` oder `POSTKAUZ_DATA_DIR`. Auf Linux und macOS gibt es das nicht.

- **Kommandozeile** schlägt Umgebung schlägt Datei: `--config` und `--data-dir` (seit S2.0/A7) vor `POSTKAUZ_CONFIG`/`POSTKAUZ_DATA_DIR`; außerdem `POSTKAUZ_SECRETS_BACKEND`, `POSTKAUZ_PASSWORD_<NAME>` (Passwort eines Kontos, nur lesen) und seit S2.1 `POSTKAUZ_POLICY` (Pfad der Policy-Datei).
- **Daten:** `postkauz.db` (SQLite, 0600), `postkauz.log` (JSON-Zeilen, 0600, ohne Inhalte und Geheimnisse), `blobs/` (Rohmails und Anhänge, [datenmodell.md](datenmodell.md), „Blob-Store"), seit S2.1 der Standardort `attach/` für `[paths] attach_dir` (PostKauz legt ihn nicht an; wer Dateien anhängen will, legt ihn selbst an). Standard: Linux `$XDG_DATA_HOME/postkauz` bzw. `~/.local/share/postkauz`, Windows `%LOCALAPPDATA%\postkauz` (lokal, nicht „Roaming"), macOS `~/Library/Application Support/postkauz`. Verzeichnis 0700 (ein vorhandenes mit weiteren Rechten verschärft seit S2.0 jedes Kommando, das es öffnet, samt Log auf 0600, Sonderbits bleiben; ein Symlink oder ein Pfad eines anderen Nutzers bleibt unverändert; Fehler und Ausnahmen nur als Warnung im Log), **nie** in einem Cloud-synchronisierten Ordner (`doctor` warnt bei OneDrive, Dropbox, iCloud u. Ä.). Angelegt wird es erst beim ersten Kommando, das es braucht; `version` und `doctor` legen nichts an.
- **Geheimnisse:** Schlüsselbund (Windows Credential Manager, macOS Keychain, Secret Service) oder Umgebungsvariable; die Datenbank enthält nur den Verweis `account/<datadir-id>/<name>` (seit S2.0; `<datadir-id>` sind 8 Hex aus der Kennung des Datenverzeichnisses, [datenmodell.md](datenmodell.md), Tabelle `meta`). Einträge mit dem alten Namen `account/<name>` zieht das erste Kommando ab Schema 8 um (außer `mcp`, der keine Passwörter anfasst); scheitert dabei nur das Löschen des alten Eintrags, warnt das Kommando auf stderr und `doctor`, bis er gelöscht ist; ist unter dem alten Namen nichts lesbar und `POSTKAUZ_PASSWORD_<NAME>` nicht gesetzt, bleibt der alte Verweis, und `doctor` nennt, worauf der Umzug wartet. Ohne Schlüsselbund gibt es keinen stillen Rückfall (siehe [sicherheit.md](sicherheit.md), Abschnitt 4).
- **`doctor`** meldet Version, Konfiguration (Pfad, vorhanden, Fehler), Datenverzeichnis, Log, Datenbank (`missing`, `ok`, `needs_migration`, `too_new`, `error`), Schemaversion (vorhanden und bekannt), Schlüsselbund (`available`, `unavailable`, `insecure`) und je Konto, woher das Passwort käme (`stored`, `environment`, `missing`) samt Status der letzten Prüfung; bei `needs_migration` (älterer Bestand, z. B. Schema 7 aus 0.1.0-rc1) liest er die Konten trotzdem (nur Name, Verweis, Status) und weist darauf hin, dass das nächste Kommando migriert; seit S2.0 Warnungen für Konten mit altem Schlüsselbund-Verweis (ohne erreichbaren Schlüsselbund mit dem Hinweis, dass der Umzug wartet und `POSTKAUZ_PASSWORD_<NAME>` weiter gilt) und für alte Einträge, die beim Umzug nicht gelöscht werden konnten oder (je umgezogenem Konto nur lesend geprüft) noch bestehen, etwa nach einem Abbruch zwischen Umstellen und Löschen; seit S1.11 den Audit-Export (Zeile `audit:` mit letztem Export, Ort, Zahl der nicht exportierten Tage und `[audit] export_dir`; Warnung, wenn ein Tag älter als zwei Tage fehlt); seit S2.1 die Policy-Datei (Zeile `policy:` mit Pfad, `found` bzw. `not found, built-in defaults` und der eingetragenen Version, oder `not recorded yet`, wenn die Datei seit dem letzten Kommando geändert wurde; `INVALID: …` mit dem Fehler) und den Ordner für Dateianhänge (Zeile `attach:`); dazu Warnungen. `doctor` trägt selbst nichts ein. Exit 1 nur bei ungültiger Konfiguration oder Policy-Datei. `--json` liefert alles als ein Objekt (u. a. `database`, `schema_version`, `keyring`, `index_pending`, `extract_pending`, `audit_last_export`, `audit_days_not_exported`, `policy_path`, `policy` (`ok`\|`default`\|`invalid`), `policy_sha256`, `policy_version` (0 = noch nicht eingetragen), `policy_error`, `attach_dir`, `accounts`, `warnings`). Seit 0.3.0-alpha.1b je Konto die unvollständigen Serverantworten (Abschnitt 2b, „Leere oder unvollständige Serverantworten“; JSON je Konto `incomplete_answers`, `incomplete_answers_last`, `incomplete_answers_at`).
- **`doctor --secrets`** (S1.11) prüft zusätzlich Dateirechte und sucht gespeicherte Passwörter, einen gesetzten `POSTKAUZ_KEY` und jedes API-Schlüssel-Muster (seit T1c auch JSON Web Tokens, `eyJ….eyJ….…`) in Log, Konfiguration, Tabellen ohne Mailinhalt und Audit-Exporten ([sicherheit.md](sicherheit.md), Abschnitt 4). Ausgabe: Abschnitt `secrets:` mit einer Zeile je Prüfpunkt (`ok`, `warn`, `fail`, `skipped`) und `result: ok` bzw. `result: N problems`; ein Fund nennt Datei und Zeile, nie den Wert. Mit Funden Exit 1 (`secret check failed`).
- **`doctor --blobs`** (A03 A5.4) prüft zusätzlich den Blob-Store ([datenmodell.md](datenmodell.md), „Blob-Store") gegen die Datenbank; `--blobs` allein prüft eine zufällige Stichprobe von 1 % (mindestens eine Datei), `--blobs=all` alle (so ruft ihn später `restore` auf), jeder andere Wert ist ein Eingabefehler (Exit 2; `--blobs all` mit Leerzeichen ebenso). Ablauf: alle Zeilen von `blobs` und alle Verweise aus `drafts.attachment_blobs` lesen, dann einmal über das Verzeichnis laufen (ohne Inhalt zu lesen), dann für die Stichprobe aus den Dateien mit Zeile oder Entwurfsverweis `Store.Verify` (SHA-256; Größe aus der Zeile, Dateianhänge von Entwürfen haben keine). Gezählt werden: geprüfte Dateien `ok`, `corrupt` (Inhalt passt nicht zum Hash oder zur Größe), `missing` (während der Prüfung verschwunden), `unreadable` (z. B. Rechte); für **alle** Zeilen `rows_without_file`; `draft_attachments` (Datei ohne Zeile, aber von einem Entwurf verwiesen: Dateianhänge legt `drafts.create`/`drafts.update` ohne Zeile ab; **nicht** verwaist), `draft_attachments_without_file`, `files_without_row` (weder Zeile noch Entwurfsverweis; unschädlich, Kandidaten für das spätere `blob gc`), `unknown_files` (falscher Name oder Ort) und `temp_files` (liegen gebliebene `tmp/put-*`). doctor ändert dabei nichts: keine Reparatur, kein Löschen, kein Eintrag in die Datenbank, kein neues Verzeichnis. Ausgabe: Abschnitt `blobs:` mit den Zahlen, je Art höchstens 10 Hashes und `result: ok` bzw. `result: N problems`; nie Inhalt, Dateinamen von Anhängen oder Betreffs. `--json`: Objekt `blobs` mit `status` (`ok`\|`problems`\|`error`\|`not_checked` samt `reason`, etwa `database missing`), `mode` (`sample`\|`all`), `rows`, `files`, `referenced`, `checked`, den Zählern oben, `problems`, `examples` (Art → Hashes) und `duration_ms`. Probleme sind `corrupt`, `missing`, `unreadable`, `rows_without_file` und `draft_attachments_without_file` (Rohmail oder Anhang verloren) sowie eine abgebrochene Prüfung: dann Exit 1 (`blob check failed: N problems`); Dateien ohne Zeile, fremde und Temporärdateien sind nur Hinweise (Exit 0). Ohne Datenbank oder bei Schema 0 meldet er `not_checked` (Exit 0). Mit 50.000 Blobs dauert die Stichprobe unter einer Sekunde, `--blobs=all` wenige Sekunden (Messung im Container, Blobs zu 2 KB).
- **Sprache:** Ausgaben und Fehlermeldungen sind Englisch (siehe CLAUDE.md); Mehrsprachigkeit ist kein Ziel des MVP.
