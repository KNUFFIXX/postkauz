# A03 — Nachbesserung T1b und Zusammenführung mit `main` (Prüfsitzung, 28.10.2026)

Auftrag der Prüfsitzung DRACO-PK09 an eine Cloud-Sitzung. Ausgangsstand: dieser Zweig `claude/magical-goldberg-lwcx1n` (`6d1d3d4`, Teil T1b, Basis `f536810`) und `main` `bac9f12` (T1a, T1c, T4, ADR-010). Es gelten `CLAUDE.md` und `auftraege/A03_teile.md` „Rahmen für alle Teile“ (Toolchain Go 1.27.3, Testserver, nie echte Postfächer/Zugangsdaten, `make check` je Commit, vor dem Push `make race`, `make integration`, `make vuln`, `make cross`). Abweichend von Rahmen 3 führt **diese** Sitzung T1b mit `main` zusammen — aber nur auf ihrem eigenen Arbeitszweig; **nichts nach `main` pushen, kein Tag, kein Release.** `main` setzt die Prüfsitzung nach Durchsicht vor.

Gegenprüfung (zwei frische Claude-Läufe, Codex, Nachprüfung jedes Funds am Quelltext mit Wegwerf-Tests): T1b PASS mit Hinweisen, kein Blocker; `main` (T4) ohne Blocker. Die Nachbesserungen unten sind die nachgeprüften Funde. Jeder Punkt bekommt einen Regressionstest, der vorher scheitert und nachher besteht (bei PowerShell: Lesetest bzw. Trockenlauf-Beschreibung im Protokoll).

## Reihenfolge

1. Eigener Arbeitszweig von `6d1d3d4`. **Teil A** (T1b-Code, Migration 0019 darf noch geändert werden, sie liegt nicht auf `main`).

## Teil A — T1b-Code

- **A-F3 (wichtig) Widerruf des letzten Schreibers:** `internal/ops/draft_push.go:340-349` prüft vor APPEND nur `created_by` und `requested_by`. Ein Agent ändert einen Entwurf des Menschen, sein Schlüssel wird widerrufen → seine Änderung wird trotzdem abgelegt (nachgewiesen: Mensch legt an, Agent ändert per `drafts.update`, Widerruf, Push → `Pushed:1 KeyRevoked:0`, abgelegte Nachricht enthält die Agenten-Änderung). Fix: letzten Schreiber des Inhalts festhalten (`drafts.updated_by`, Spalte in Migration 0019 ergänzen) und in der Herkunftsprüfung mitprüfen. Default (Festlegung, Einspruch möglich): kein APPEND; Entwurf eines Agenten → `abandoned` wie bisher; **Entwurf des Menschen, den nur ein Agent geändert hat → zurück auf `draft` mit Systemereignis/Hinweis, Freigabe `rejected`** (der Mensch verliert seinen Entwurf nicht). Regressionstest: genau dieser Ablauf → `KeyRevoked=1`, 0 APPENDs.
- **A-F4 (wichtig, Regression gegenüber `f536810`) `audit verify` übersieht eingeschobene Zeilen:** `internal/ops/auditexport.go:232-238` liest exportierte Tage nur über ihren gespeicherten ID-Bereich, der Plan (`:203-207`) nur offene Kandidaten. Eine Zeile mit freier niedriger ID (z. B. −1 oder 0) und dem Zeitstempel eines abgeschlossenen Tages fällt aus der Prüfung; `6d1d3d4` meldet `ok`, `f536810` meldete `database_changed`. Fix: Zählabgleich (Zeilen mit `id ≤ LastEventID` des letzten abgeschlossenen Tages = exportierte Einträge + offene Zeilen bis dahin) oder je Tag zusätzlich nach Zeitstempel laden; teuer darf es nicht werden (Grund für T1b-Umbau). Regressionstest: Einschub → `database_changed`.
- **A-F9 (wichtig) tote Starts:** `internal/store/audit_query.go:191` und `internal/cli/doctor.go:380-391`. Wird `sync --watch` über die Aufgabenplanung beendet (harter Abbruch, `root.go:133` reagiert nur auf Strg+C/SIGTERM), bleibt ein `started` ohne Abschluss für immer; `doctor` warnt dauerhaft, spätere Abnahmen an Kopien scheitern an `audit_unfinished_calls == 0`. Außerdem blendet eine gehaltene Kontosperre die offenen `sync.run`-Starts **aller** Konten aus. Fix: Beim Holen einer Kontosperre die offenen `sync.run`/`import.run`-Starts dieses Kontos mit einem Abschluss `error`/`process_ended` (mit `ref_id`, nur anhängen) abschließen; `doctor` blendet nur noch je Konto aus. Regressionstests: (a) offener `sync.run`-Start ohne Sperre, danach `sync` → Abschluss mit `ref_id`, `AuditOpenStarts` = 0; (b) Sperre von Konto A gehalten, toter Start von Konto B wird gezählt.
- **A-F5 (Testlücke, wenn Zeit):** Pflichttest A1 startet mit Schema 17/T1a-Export. Zweiter Pflichttest mit Testdaten, die der Stand rc8 (`99a7cc0`, Schema 16) erzeugt, inklusive eines verspäteten Eintrags, den rc8 in einen alten Tag neu exportiert, und eines offenen Tages; dann 16 → 19, `audit verify` ok, neuer Export lässt alte Tage unverändert, `verify` wieder ok. Generator nach dem Muster von `internal/ops/testdata/t1b_schema17/gen/`.
- **Kommentare:** `internal/cli/doctor.go:372` („Lange Läufe … schreiben je Runde eigene Einträge“ widerspricht `AuditOpenStarts` und `docs/sicherheit.md`); `internal/policy/file.go:54`, `:100` „ab so vielen“ → „über“ (Prüfung ist `>`). Die Obergrenze von `bulk_confirm_threshold` bleibt bei T2.

## Teil B — T4-Code (nach dem Merge)

- **B-M4 (wichtig) `doctor` zeigt keinen Refresh-Fehler:** `internal/cli/doctor.go:292-314` liest nur `oauth.Load`; E11 verlangt „Hinweis in `doctor`“. Fix: je OAuth2-Konto letztes Audit-Ereignis `oauth.refresh` (Ziel `account:<name>`) lesen; ist es `error` und nicht älter als der gespeicherte Token, Warnung „account X: last token refresh failed (<code>, <Zeit>); sign in again with: postkauz account login X“ und Feld `token_refresh` im JSON; ein späteres `ok` oder neues Login hebt sie auf. Andere Lesefehler (z. B. Zeitüberschreitung) nicht still als `unknown` lassen. `docs/cli.md` nachziehen. Regressionstest in `internal/cli/s37_test.go` (Ereignis direkt ins Audit schreiben, wenn kein Fake-IMAP greifbar).
- **B-M1 Token-Teile:** `internal/oauth/store.go:267` verwirft Löschfehler der Teile; `account remove` meldet dann `secret_deleted: true`, Teile bleiben unauffindbar liegen. Fix: Fehler außer `ErrNotFound` zurückgeben; Haupteintrag nur löschen, wenn alle Teile weg sind. Regressionstest mit fehlschlagendem Delete eines Teils.
- **B-M3 `doctor --secrets`:** `internal/cli/doctor_secrets.go:105-108` überspringt die Refresh-Token-Suche still, wenn `oauth.Load` scheitert. Fix: `Skipped`-Eintrag mit Detail `keyring: <fehler>` wie im Passwort-Zweig. Regressionstest.
- **B-M2 Audit `oauth.refresh`:** `internal/ops/oauth.go:130` verwirft den Fehler von `Append`. Fix: als Warnung loggen (ohne Token), Sync nicht abbrechen. Regressionstest mit scheiterndem Audit-Writer, Log enthält kein Geheimnis.
